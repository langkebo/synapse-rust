# 06: 阅后即焚的过期处理改为批量标记

**What to build:** 阅后即焚的过期扫描对每条待处理记录串行执行四次数据库往返，其中「标记为已处理」是一次一条的单独更新。积压 N 条就是 4N 次串行往返，在 1000 条积压下会独占 worker 数秒，拖慢整个队列消费。本票把「标记为已处理」合并为一次批量更新，先把往返次数从 4N 降到 3N+1。

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

**审计条目：** #4（🟡 Medium）性能部分 — burn-after-read 逐行串行 DB 写

**范围说明：** 本票只做**性能**改造，不改变任何失败语义。重复 redaction 的正确性问题由 07 单独处理，本票不得顺带改动判定逻辑。

- [ ] 「标记为已处理」由逐条更新改为一次批量更新（单次 `WHERE id = ANY(...)`）
- [ ] 批量更新为空集时直接跳过，不产生多余的数据库往返
- [ ] 标记成功与失败的语义、日志字段与改动前保持一致（不得吞掉错误）
- [ ] 存储层的 trait、真实实现与测试替身三处同步提供批量接口，不出现单侧缺失
- [ ] 相关 crate 的既有测试全绿，`cargo clippy -- -D warnings` 无告警
