# 前缀命名空间治理方案（ISSUE-13 收口）

- 日期：2026-10-08
- 范围：`synapse-rust`（路由注册）↔ `matrix-js-sdk`（契约门禁）↔ `Tjg`（唯一消费者）
- 现状基线：后端 `e17efb937`；路由总数 1159

---

## 0. 结论先行

ISSUE-13 的表述是「私有端点必须走 `/_matrix/vendor/v1`，不要污染标准前缀」。
按字面执行，第一反应是「把那 ~150 条路由改名」。但看完仓库自己的规则后，结论要改成三条：

**① 正确做法是一次性原地替换，不是"加 vendor 别名 + 保留 client 别名"。**
`synapse-rust/AGENTS.md` 铁律 1 明确规定：

> **项目状态：未发布、无外部用户、无生产数据。** 因此**不存在向后兼容义务**。
> 不得为"向后兼容"保留旧路径别名、双实现……
> **判据**：如果某符号/分支/配置的唯一存在理由是"兼容旧行为"，就删掉它。

**② 现在这种"双挂载"的迁移方式本身就违反铁律 1，而且正是迁移停滞的原因。**
`friend_room.rs` 里写着「ISSUE-13: vendor 前缀（私有端点，client 前缀保留为向后兼容别名）」——
按铁律 1 的判据，这个别名应当直接删掉。它没被删，反而成了"已迁移"的范式被复制：
每迁一个模块要手抄两遍路由，成本翻倍，所以迁了 5 个就停了。

**③ 那 68 条 client 别名已经是死代码——Tjg 早就不调它们了**（见 §2.4 取证）。
即：**当前状态不是"迁移做了一半"，而是"迁移做完了，旧的一半忘了删"。**

**④ 真正待办的量比"150 条"小得多**：需要新增 vendor 挂载的只有 **~91 条**（§1.1），
另 68 条只要删；而 ~119 条**必须留在标准前缀**（其中 18 条 MSC 端点应走 `unstable/`），
搬走反而是标准合规性倒退。

**⑤ 最该先修的是门禁**：它现在判的是"5 个模块名"，所以绿的；而真正的判据
（ISSUE-13 原计划要求的 spec 白名单）**从未被实现**（§2.1）。这是"绿门禁掩盖问题"的典型。

## 2. 根因（四条，均带证据）

### 2.1 门禁从「spec 白名单」退化成了「5 个模块名」

ISSUE-13 的原始计划（`docs/superpowers/plans/2026-08-10-sdk-remaining-work-plan.md` Task D2）要求：

> **Step 1: 写契约门禁**——标准前缀路径必须存在于 Matrix spec 路径白名单，否则 fail。
> Files: Create `scripts/quality/check-standard-prefix-whitelist.mjs`

实际落地的是 `matrix-js-sdk/scripts/quality/check-vendor-prefix-migration.mjs`：

```js
const PRIVATE_MODULES = ["friend", "voice", "key-rotation", "burn-after-read", "external-service"];
// 判据：该目录下的 .ts 里有没有 `prefix: ClientPrefix.V1|V3|R0`
```

后果：

- `space`/`widget`/`room_summary`/`dm`/`push_notification`/`moderation` **完全不在扫描范围内** → 门禁绿，污染依旧
- 判据是「SDK 源码里有没有出现某字符串」，而非「这条路由属于哪个命名空间」→ 分不出 §1 的三类
- `check-standard-prefix-whitelist.mjs` **从未被创建**

**这是"门禁绿但问题在"的直接原因。**

### 2.2 后端缺「前缀归属」这一层数据

`RouteEntry`（`synapse-web/src/routes/route_ledger.rs:77`）已有成熟的元数据模式：

```rust
pub struct RouteEntry {
    pub method: Method,
    pub path: &'static str,
    pub registered_by: &'static str,
    pub query_params: &'static [&'static str],
    pub auth: Option<&'static str>,        // 已有：鉴权要求
    pub rate_limit_exempt: bool,           // 已有：限流豁免（B-4 自动派生）
}
```

`create_router` 已经**从 ledger 自动派生**限流豁免表。
换言之：「给每条路由打策略标签，再由它自动派生运行时行为」这套机制**已经存在**，
只缺 `prefix_policy` 这一个字段。

> 注意铁律"推论"：新增路由元数据字段若**没有下游消费方**属冗余，必须补齐消费方或删除。
> 本方案的消费方就是 §3 Phase 1 的守卫 —— 这一点必须同时落地，不能只加字段。

### 2.3 后端有一个"专为此场景写的助手"，但生产代码零调用

`route_ledger.rs:135`：

```rust
/// Expand a set of `(Method, relative_path)` tuples across a list of nest prefixes …
/// 这是「把同一个 inner router 挂在多个前缀下」这一常见模式的便利函数
/// —— 手写多份既啰嗦又容易出错。
pub fn expand_under_prefixes(registered_by, prefixes, paths) -> Vec<RouteEntry>
```

实测：**全仓只有它自己的单测调用它**（`route_ledger.rs:332`），生产代码零使用。

同时 `space.rs:173` 已经用上了紧凑的运行时惯用法：

```rust
Router::new().nest("/_matrix/client/v1", router.clone()).nest("/_matrix/client/v3", router)
```

而"已迁移"的 `friend_room.rs` 却是**手工逐条重复声明**（30+ 行）。
三者合起来说明：**正确工具已写好且被文档化，但没被采用**；实际采用的是成本最高、最易漂移的手写双份。
这与 §2.4 合起来解释了为什么迁移只做完 5 个模块。

### 2.4 旧别名已是死代码，但没人删（取证）

Tjg 的路径常量早已全部指向 vendor：

```ts
// Tjg/src/services/matrix/paths/friends.ts:4
LIST: PREFIX_VENDOR_V1 + '/friends',
// Tjg/src/services/matrix/paths/voice.ts:4
CONFIG: PREFIX_VENDOR_V1 + '/voice/config',
```

全仓检索 `_matrix/client/v[13]/friends` → **0 命中**。
即那 68 条 client 别名已无任何消费者，唯一存在理由就是"兼容旧行为" ——
按铁律 1 的判据，**早就该删**。

它们之所以还在，是因为后端把它们当成"迁移的正当产物"（注释写着"保留为向后兼容别名"），
于是没有任何机制会去清理它们。

## 3. 方案：三阶段一次做完，不留兼容层

### Phase 0 — 分类清单（不改代码，先评审）

产出 `synapse-rust/docs/prefix-policy.json`（机器可读、可评审）：

```json
[
  { "module": "space", "path": "/spaces/{space_id}/hierarchy", "methods": ["GET"],
    "policy": "msc", "msc": 2946, "note": "已稳定，必须留 client 前缀" },

  { "module": "space", "path": "/spaces", "methods": ["POST"],
    "policy": "vendor", "canonical": "/_matrix/vendor/v1/spaces" },

  { "module": "friend_room", "path": "/friends", "methods": ["GET", "POST"],
    "policy": "vendor", "canonical": "/_matrix/vendor/v1/friends",
    "note": "client 别名已无消费者，按铁律 1 删除" }
]
```

**为什么必须人工评审**：`room` 97 条里 93 条标准、`thread` 21 条里 18 条 MSC。
把"该留 / 该改 / 该删"变成一次可评审的决策，而不是散在 91 个 `.route()` 调用里。

**验收**：清单覆盖 `/_matrix/client/{v1,v3}` 下全部 614 条路由，无遗漏。

### Phase 1 — 让 policy 成为一等公民，并让门禁按 spec 判

> **✅ 已实施（2026-10-08，commit `0ad43b242`）——但实现方式与本节原提议不同，见 §8。**
> 结论先行：**没有**给 `RouteEntry` 加 `PrefixPolicy` 字段。台账是**纯路径驱动**的，
> 因此零 Rust 改动、零 ledger/fixture 抖动。下文保留原提议是为了记录取舍过程，
> **请勿据此再去实现那个字段**（按 AGENTS.md 铁律 1 的推论，无消费方的路由元数据字段属冗余）。

1. ~~`RouteEntry` 加字段（照 `rate_limit_exempt` 的既有模式）~~ → 见 §8，未采用：

```rust
pub enum PrefixPolicy {
    /// 稳定规范端点，必须在 /_matrix/client/{v1,v3}
    Standard,
    /// MSC 提案，必须在 /_matrix/client/unstable/<msc>/
    Msc { msc: u32 },
    /// 厂商私有，唯一规范位置是 /_matrix/vendor/v1
    Vendor,
}
```

注意**没有 `CompatAlias` 变体** —— 按铁律 1，兼容别名不是一个合法状态。

2. 提取器在前缀解析时一并标注 policy。`extract_registered.py` **已经递归解析 `.nest()`**
（`ROUTE_CONTRACT.md:18`：「已递归应用 `.nest("/prefix", ..)` 与 `expand_under_prefixes(..)` 的前缀」），
所以只需记录每个挂载是 `vendor` 还是 `client`。

3. 新增守卫 `test_extract_registered.py::check_prefix_policy()`，判据：

| 判据 | 失败含义 |
| --- | --- |
| `policy ∈ {Standard, Msc}` 的路径必须命中 spec/MSC 白名单 | 有人把私有端点标成了标准端点 |
| `policy = Vendor` 的路径必须在 `/_matrix/vendor/`，且 canonical 存在 | 标了私有但没落 vendor |
| **`/_matrix/client/{v1,v3}` 下出现 Vendor 端点** | 污染回潮（= 现存的 68 + ~91 条） |
| **`/_matrix/client/v3|v1` 下的地址在清单里查不到** | 新增路由未分类（防漏审） |

**这个守卫直接复用现成范式**：`check_non_namespace_bucket()` 就是把「前缀之外」桶
精确钉死为 8 条，它的 docstring 正好写了本次要做的事的哲学：

> "Pinning a defect in place as if it were the contract is how an anomaly becomes permanent:
> the assertion documented the problem instead of forcing the decision."
> （把缺陷钉成契约，就是让异常永久化）

**验收（铁律 8：门禁必须自证能变红）**：`check_route_contract.sh` 已用
`test_extract_registered.py --mutation-check` 做这件事。新守卫照做：
注入一条"vendor 路由挂在 client 前缀"的用例，要求套件转红。

### Phase 2 — 一次性原地改（无别名、无过渡态）

对 §1.1 的三组分别处理，**同一个提交批次内完成**：

| 组 | 动作 |
| --- | --- |
| 已迁移的 5 个模块 | **删除 client 挂载**（`friend_room.rs` 等 30+ 行别名） |
| 未落地的 ~91 条 | 把 client 挂载**改**为 vendor 挂载（6 个模块） |
| MSC/规范端点 | 留在原处 + 登记 policy；18 条 MSC 若要挪，目标是 `unstable/<msc>/` 而非 vendor |

实现上用 §2.3 已存在于代码库的惯用法，避免手抄：

```rust
let inner = Router::new()
    .route("/spaces", post(create_space))
    .route("/spaces/{space_id}", get(get_space).put(update_space).delete(delete_space))
    /* … 全部写相对路径 … */;

// 唯一挂载点；policy 随挂载进入 ledger
Router::new().nest(VendorPrefix, inner)          // → PrefixPolicy::Vendor
```

**顺带清理冗余**（铁律 2「同一职责只允许一份实现」）：
`expand_under_prefixes` 若在改造后仍无生产调用，按铁律 1 删除；不得留两套前缀机制并存。

**验收**：`cargo nextest` 相关批次绿 + `bash scripts/contract/check_route_contract.sh` 绿 +
`(method, path)` 变化**只包含预期的删除与改名**（用 `git diff` 逐条核对，不能多也不能少）。

### Phase 3 — 下游同步（不是兼容层，是一次协同改名）

```
后端改路由 → 重导 ledger → SDK contract:sync + codegen
          → 重打包 tarball → 刷新 Tjg pin → Tjg 路径常量跟进
```

按工作区 `CLAUDE.md` 的 PR 顺序（后端 → SDK → 前端），回滚反向。

**没有"保留别名等客户端跟上"这一步** —— 因为项目未发布、无外部用户，
Tjg 是唯一消费者且在同一工作区内，属于一次协同改名。
唯一要注意的是 `Tjg/meta/sdk-pin.json` 的 `sdk_commit` 必须与 SDK HEAD 一致。

### Phase 4 — SDK 门禁改为从同一来源派生

`check-vendor-prefix-migration.mjs` 的 `PRIVATE_MODULES` 常量删除，改为读同一份 policy；
并补上 ISSUE-13 原计划里**从未创建**的 `check-standard-prefix-whitelist.mjs`
（「标准前缀路径必须存在于 spec 白名单」）—— 这条正是 §1 里 A 类 ~588 条的守卫。

**验收**：后端把某模块从 `standard` 改成 `vendor` 后，SDK 门禁必须**跟着变红**并指出该模块。
现在做不到，所以才出现"后端还有 91 条没落地、SDK 门禁却是绿的"。

## 4. 需要注意的既有约束

| 约束 | 影响 |
| --- | --- |
| `derived_route_table*.inc.rs` 是**生成物**，生成器要求 6 份 fixture 逐字节复现 | 必须先改 `.route()` 代码再重生成；手改表无效 |
| `check_route_contract.sh` 会跑 `--mutation-check` | 新守卫必须可被证伪（铁律 8），不能写成恒绿 |
| `check_sdk_route_coverage.py`（B2-4b）强制「SDK 真实调用 ⊆ 后端已登记」 | 删后端路由会让它红，这**正是期望行为** —— 它逼着 SDK 同步改，不能漏 |
| MSC4204/4267 改动曾因漏录 `scripts/shell_routes_allowlist.txt` 直接红 CI | 路由行号漂移后要同步该 allowlist |
| `/_matrix/vendor/v1` 不在 Matrix 规范枚举的命名空间内 | 它是本项目自定约定。既已有 68 条在用，**建议保持不换**，但应补一份 ADR 记录该选择，避免后人误以为是规范要求 |
| MSC 提案的正确归属是 `/_matrix/client/unstable/<msc>/` | §1 里 18 条 MSC 端点若要从 `v1` 挪动，目标应是 `unstable/` 而不是 `vendor/`；但「留在 v1」也可能是有意的（稳定化在即），需在 Phase 0 逐条裁定 |
| 未发布项目 | 唯一的"兼容性"约束来自同一工作区内的 Tjg，而它是协同改名的对象，不是外部依赖 |

## 6. 工作量估计

| 阶段 | 内容 | 估计 |

| Phase 0 | 614 条分类 + 分批评审 | 主要成本是评审，2-3 人日 |

**建议先做 Phase 0 + Phase 1**：它们不改任何路由，
零风险，但会把"绿门禁掩盖问题"这个最危险的状态终结掉 ——
之后每一条待办都是显式可见、可派工的。

## 7. 一句话总结

这个问题**不是"150 条路由要改名"**，而是：

> 迁移早该做完了 —— 68 条别名已经是死代码，
> 真正需要动的只有 ~91 条；
> 让它看起来没做完的，是一个**判错对象的门禁**（判"5 个模块名"而不是"路径是否在 spec 白名单"），
> 和一种**违反本项目自己铁律 1 的迁移方式**（保留兼容别名，导致成本翻倍而停滞）。

### 8.2 守卫的三条判据

| 判据 | 内容 | 堵住的失效 |
| --- | --- | --- |
| **A** | 台账每条必须真实存在 | 台账腐烂（登记了却已不存在的路由）—— 双向棘轮，与 `extract_unresolved_allowlist.txt` 同款 |
| **B** | 整模块私有文件里的 client 前缀路由必须**全部**登记 | 在这些模块新增私有端点而不分类 |
| **C** | 该桶条数 ≤ `LEDGER_CEILING`（当前 169） | 任何增长；**口径与 policy 标注无关，因此改标签绕不过去** |

`LEDGER_CEILING` 刻意取**实测值本身（169）而不留余量** —— 留余量等于给"再污染 N 条"发通行证，
而本门禁的全部意义就是不让你再加。理论下限是 5（那 5 条 MSC 端点合法保留）。

### 8.3 与原提议的差异，以及为什么

**原提议**：给 `RouteEntry` 加 `PrefixPolicy` 字段，由提取器在解析 `.nest()` 时标注。

**实际做法**：**不加字段**，纯路径驱动（`path.startswith(CLIENT_PREFIXES)`）+ 台账文件。

放弃加字段的理由：

1. **不需要。** 判据本来就是"这条路径在不在 client 前缀下、该不该在"，这是**路径自身的属性**，
   不需要从路由注册处搬运。ISSUE-13 原计划要的也是「spec 路径白名单」，同样是路径驱动。
2. **代价高。** `derived_routes.rs` 与三份 `.inc.rs` 是生成物，且生成器要求 6 份 fixture
   **逐字节复现**。给行模型加字段会连带改动生成器、生成表、fixtures、SDK 的 `contract:sync`
   输入 —— 全是跨仓库抖动，而收益为零。
3. **违反铁律 1 的推论。** AGENTS.md 明确写着「新增的路由元数据字段若没有下游消费方，属冗余」。
   这里下游（守卫）根本不需要该字段就能判定，所以加它就是冗余。

**保留的相似之处**：三条判据的精神与原提议一致（标准→必须命中白名单、vendor→必须在 vendor 前缀、
client 下出现 vendor 路由→红）。差别只在**数据放在哪**：原提议放 Rust 行模型，实际放可评审的台账文件。
台账文件的好处是分类理由（"为什么这条是 vendor"）有地方写，而枚举字段只能放一个枚举值。

### 8.4 顺带修掉的脚手架缺陷

`test_extract_registered.py::mutation_check()` 的 mutation#6 成功分支里有一句提前 `return bad`，
会**静默跳过其后注册的所有变异** —— 我新加的 mutation#7 一开始根本没被执行到
（第一轮输出里只有 mutation#5/#6，没有 #7）。这与铁律 8 说的
"看到长期全绿的门禁，先怀疑它没在工作"是同一类。已改为落空（fall through），
并留注释说明为什么不能在这里 `return`。

### 8.5 已知缺口（未假装覆盖）

**混合模块不做全覆盖断言**：`room.rs`（97 条 client 前缀，93 条标准）、`moderation.rs`、
`handlers/thread.rs` 只逐条登记已识别的私有端点，但**不**断言"该文件里所有 client 前缀路由都已分类"。
原因是那需要一份机器可读的 spec 路径清单（ISSUE-13 原计划的正向方向），属独立议题。
后果：在 `room.rs` 里新增一条私有端点**不会**被 B 判据抓到。

补齐路径（Phase 1b）：引入一份可校验的 spec 路径清单。诚实的做法是**从机器可读的规范副本生成**
（而不是手抄 —— 手抄 588 条必然漂移），并让它只作为"正向白名单"使用，与台账互相校验。

### 9.2 破环：`gen_derived_routes.py --bootstrap`

**撞到的硬阻塞**：路线面一变，`gen_derived_routes.py` 的 fixture 保真校验就必然红，
而它是**写表前**的硬门禁；但 fixture 是**从这张表**渲染出来的
（`synapse_ledger_export` 读 `declared_ledger_all()`）。于是"真删了路由"这件事
**在数学上不可能**先满足校验再写表 —— 循环依赖。实测：删完 77 条后
`--check` 报 6 组 lane/profile 全部 `missing=[...]`，`--bootstrap` 之前无路可走。

历史提交（`GATE_INTEGRITY_FOLLOWUP_2026-09-19_LOG.md` §10.2：`+16/−1` 只多 3 行）说明
上一次也不是走生成器，而是**手改生成表** —— 手改 77 条显然不可接受。

**修法**：给生成器加显式 `--bootstrap`（默认关闭，与 `--check` 互斥）：
跳过保真校验写表，但**把红色保真报告原样打印**，并明确要求随后重导出两条车道、
再跑一次 `--check` 才算认证。CI 只会跑到 `--check`，因此这个开关没有放宽任何门禁。

正确的流程固化为：

```
gen_derived_routes.py --bootstrap     # 写表；此时保真必然红
generate_sdk_ledger_fixtures.sh       # SDK 车道
synapse_ledger_export --profile=...   # golden 车道 ×3
gen_derived_routes.py --check         # 真正的双向交叉认证（本次 EXIT=0，1084 行 / 6 组 fixture）
```

### 9.3 别名删除暴露出的**生产代码耦合**（本批最值得记的发现）

（而不是路径形状正则）做全仓扫描，扫出 4 处生产代码把语义**钉在了 client 别名上**：

### 9.4 守卫自证：mutation#7 的一条位置代理失效

`test_extract_registered.py` 的 mutation#7/"unlisted route" 用 `sorted(real_ledger)[0]`
选"被删条目"，那是**位置代理**：它只在字典序第一条恰好落在整模块私有文件里时才证明得了

这正是铁律 8 的价值：它不是被本次改动弄坏的，而是**一直在那儿、只是恰好还成立**。
