## 5. element-hq/synapse 设计模式 + 本仓可执行的修复方案

### 5.1 B-1.1 admin 踢人 — synapse 设计参考

**synapse 怎么做的**（`synapse/handlers/admin.py`）：
- `AdminHandler.shutdown_room` 走 `task_scheduler` 把 `_redact_all_events` 派发为**后台任务**
- 返回 `shutdown_room_result` token，前端用 `/admin/shutdown_room/<id>/status` 轮询进度
- 单用户的批量移除**不在**请求路径同步做——避免长请求拖死 worker

**本仓可执行方案**（小改 + 风险低）：

```rust
// admin_user_service.rs:234-241  当前
for room_id in &joined_rooms {
    match self.member_storage.remove_member(room_id, user_id, None).await {
        Ok(()) => removed.push(room_id.clone()),
        Err(e) => failures.push(AdminEvictionFailure { ... }),
    }
}
if !removed.is_empty() {
    let _ = self.room_storage.decrement_member_counts_batch(&removed).await;  // 🔴 静默吞错
}
```

**修法**：
1. **限速并发**——改为 `futures::stream::iter(joined_rooms.iter()).map(|room_id| async { ... }).buffer_unordered(8)`（限流 8 防连接池耗尽，synapse 默认 `evict_max_concurrency = 8`）
2. **`let _ =` 改 `warn!`**——`tracing::warn!(error = %e, "decrement_member_counts_batch failed; room_summaries.updated_ts may be stale")`（这是 5 行内能改的）
3. **范围截断**——`membership/mod.rs:360` 的 `get_joined_rooms(user_id)` 改为 `LIMIT 1000`，分页游标（如果单用户加入 >1000 房间，1 次踢人必然出问题）

**工作量**：0.5d（**最高 ROI 之一**——管理后台直接受益）

### 5.2 B-1.4 friend fan-out 28 shard 串行读 — synapse 设计参考

**synapse 怎么做的**（`synapse/storage/databases/main/devices.py` + `account_data.py`）：
- 用 `account_data.MAX_USERS_PER_ACCOUNT_DATA_UPDATE = 100` 限制批大小
- 用 `_get_account_data_for_user_in_room` 单 SQL 一次拿**所有**目标数据，**不用**逐 key 循环
- 写用 `UNNEST($1::text[])` 把 array 平铺到 VALUES，单 INSERT 处理 N 条

**本仓可执行方案**（中等改）：

```rust
// friend_room_service/mod.rs:1257  当前——逐 link 串行
for link in links {
    let shards = self.friend_storage.get_friend_list_all_shards(&link.friend_room_id).await?;
    for (state_key, shard_content) in shards { ... }
}
```

**修法**：
1. **DB 读并发**——`get_friend_list_all_shards` 已经是单次 SQL（28 shard 内部处理），外层 link 循环改为 `buffer_unordered(8)` 限流并发
2. **state event 写已并发**（`try_join_all` 注释已说明）——**这部分 B-1.4 Phase 2 已做**
3. **真正的去 N+1**——把 `get_friend_list_all_shards` 改为接受 `Vec<String>` 一次查多 link，**单次 SQL** 拿全量

**工作量**：1d（中等风险——28 shard 设计是性能敏感，回归测试必跑 `friend_room_service` integration test）

### 5.3 B-2.2 event_notifier 5s/2s 硬编码 — synapse 设计参考

**synapse 怎么做的**（`synapse/notifier.py`）：
- `_WAKEUP_SLEEP_MS = 50` 唯一常量
- 长轮询 `timeout = request.GET.get("timeout", "20000")`（默认 20s，**直接由客户端传**）
- 所有 timeout 都在 `synapse.config` 字段里

**本仓可执行方案**（小改）：

```rust
// event_notifier.rs:531, 550, 760, 785, 813  当前硬编码
tokio::time::timeout(tokio::time::Duration::from_secs(5), ...).await
```

**修法**：
1. `EventNotifier` 加 `sync_long_poll_timeout: Duration` + `sync_short_poll_timeout: Duration` 字段（builder pattern 已有）
2. `start_sync_listener` 等函数接受 `timeout: Duration` 参数
3. 5 个 timeout 点改读配置
4. `ServerConfig::server::*` 加 `sync_long_poll_timeout_secs` / `sync_short_poll_timeout_secs` 字段（默认 5/2）

**工作量**：0.3d（**最高 ROI 之一**——纯机械替换，不动逻辑）

### 5.4 B-3.1 missing_docs ratchet — synapse 设计参考

**synapse 怎么做的**：
- 直接 `#![deny(missing_docs)]` 在 crate root
- 任何缺文档直接 deny——**强制写文档**

**本仓可执行方案**（小改但影响面大）：

**短期（推荐）**：
- 7 个 crate 各自的 `lib.rs:4` 保持 TODO 注释（"B2-TODO: Change to #![warn(missing_docs)] once sub-modules have docs"）
- 新加 `scripts/check_missing_docs_ratchet.sh` 跑 `cargo doc --no-deps --all-features 2>&1 | grep "warning: missing"` 输出当前 missing 数量
- 用 ratchet 法：**每次 PR 必须减少 N 个 missing docs**，禁止增加
- 计划：1-2 sprint 把 missing 数降到 < 50 → 切换到 `#![warn(missing_docs)]`

**长期**：
- 全部 0 → `#![deny(missing_docs)]`

**工作量**：3-5d 集中写文档（这是文档工作而非代码，可分散给团队）
