## 1. ⚠️ 首先更正：一个被否证的初始假设

### 1.1 初始怀疑

初读 `src/web/routes/auth_compat.rs` 时，`check_login_lockout` 的匹配写法构成一个典型的 fail-open 嫌疑：

```rust
match cache.get::<u32>(&key).await {
    Ok(Some(count)) if count >= LOGIN_MAX_ATTEMPTS => Err(ApiError::rate_limited_with_retry(...)),
    _ => Ok(()),          // ← 若 Err 可达，则缓存故障 = 放行
}
```

配合 `default_login_lockout_fail_open() -> bool { true }`（`synapse-common/src/config/security.rs:123-126`），
很容易得出"Redis 故障时暴力破解保护完全失效"的结论。**我据此写了初版报告草稿。**

### 1.2 实验推翻该结论

构建一个 Redis 不可达的 `CacheManager`（`redis://127.0.0.1:1`，tcpmux 保留端口，连接立即被拒）后直接探测：

```
DIAG get(cold)        => Ok(false)      // 即 Ok(None)，冷键读取
DIAG set              => Ok("ok")
DIAG get(after set)   => Ok(Some(7))    // 本地层确实持久化了写入
DIAG get_checked      => Ok(Some(7))
DIAG is_redis_enabled => true
```

**结论：`CacheManager::get()` 在 Redis 故障时返回 `Ok(None)`，永不返回 `Err`。**

根因在缓存层设计（`synapse-cache/src/manager.rs:511-537`）：
```rust
// L2: Redis Cache
if self.use_redis {
    if let Some(redis) = &self.redis {
        if let Some(val) = redis.get(&key).await {   // ← RedisCache::get 故障时返回 None
            ...
        }
    }
}
Ok(None)                                             // ← 故障被折叠成"缓存未命中"
```

而 `RedisCache::get`（`synapse-cache/src/remote.rs:150-171`）的文档明确写着：
> "Returns `None` for both cache miss and any backend failure (circuit breaker open, timeout, transport error).
> Callers requiring failure visibility should use `get_checked` instead."

⇒ **`auth_compat.rs` 的 `_ => Ok(())` 分支不可达**，它不是 fail-open 漏洞。
⇒ **L1 本地缓存才是 Redis 故障时真正兜住锁定的机制** —— 这恰好就是用户选定的"策略 B"。

**因此初版报告的核心指控不成立，已整体重写。** 保留此节是为了记录否证过程，避免后续审查重复该推断。

## 2. 🔴 确认缺陷（源自 §1 的实验）：`CacheManager::set()` 丢弃 TTL 参数

### 2.1 缺陷

`synapse-cache/src/manager.rs` 的 `set()` 在本地层调用的是**无 TTL 版本**：

```rust
pub async fn set<T: Serialize>(&self, key: &str, value: T, ttl: u64) -> Result<(), ApiError> {
    if let Ok(val) = serde_json::to_string(&value) {
        self.local.set_raw(key, &val);                    // ← ttl 未传入
        if self.use_redis {
            if let Some(redis) = &self.redis {
                let _ = redis.set(key, &val, ttl).await;  // Redis 分支用了 ttl
            }
        }
    }
    Ok(())
}
```

而 `LocalCache::set_raw`（`synapse-cache/src/local.rs:116-128`）的注释自述：
> `// 无 per-key TTL 的普通写入：清除旧 deadline，回落到 builder 级 TTL`

**具备 per-key TTL 能力的 `set_raw_with_ttl` 早已存在**（`local.rs:132`），且已有测试覆盖
（`d1_set_raw_honors_per_key_ttl_in_local_cache`、`d1_set_raw_long_ttl_survives_short_window`），
但 `set()` **没有使用它**。

### 2.2 实测证据

在 `time_to_live = 3600`（builder TTL 1 小时）的 manager 上写入 `ttl = 1` 秒：

```
DIAG ttl-probe immediate => Ok(Some(42))
DIAG ttl-probe after 2s  => Ok(Some(42))     ← 按契约应为 None
test ... FAILED
```

⇒ **per-write TTL 对本地层完全无效。**

### 2.3 对登录锁定的具体影响

`record_login_failure` 以 `LOGIN_LOCKOUT_TTL_SECS = 900` 秒写入计数键
（`src/web/routes/auth_compat.rs:403-404`）。但本地层实际保留时长为 **`CacheConfig::time_to_live`**：

| 层 | 实际生命周期 | 是否符合 900s 契约 |
|---|---|---|
| Redis | 900s（`redis.set(key, val, ttl)` 使用了 ttl） | ✅ |
| **本地 L1** | **builder TTL**（默认 **7200s**） | ❌ **超出 8 倍** |

**后果**：
- Redis 正常时，L1 条目被 L2 回填/覆盖，实际行为由 Redis 的 900s 主导（缺陷被掩盖）
- **Redis 故障时**（即 L1 独立支撑锁定），一个 `(ip, username)` 的失败计数会被保留
  **长达 2 小时**，远超配置的 15 分钟锁定窗口
- ⇒ 用户可能被**远超配置时长地拒绝登录**，且运维无法通过配置调整本地保留窗口

> 这与"fail-open"方向相反：是**过度保留**（可用性问题），但同样是安全控制未遵守配置契约。
> 反向情形同样存在：任何以短 TTL 写入的缓存条目都会在 L1 停留最长达 builder TTL，
> 造成**陈旧数据超期存活**。

### 2.4 修复（已实施，§5 有验证证据）

```rust
// synapse-cache/src/manager.rs — set()
self.local.set_raw_with_ttl(key, &val, Duration::from_secs(ttl));

// synapse-cache/src/manager.rs — set_checked()  同一问题，一并修复
self.local.set_raw_with_ttl(key, value, Duration::from_secs(ttl));
```

**新增回归测试**（`synapse-cache/src/tests.rs`）：
- `set_honours_per_write_ttl_for_local_tier` —— 写入 ttl=1s（builder=3600s），断言 2s 后条目消失
- `get_returns_ok_none_when_redis_is_unreachable` —— 固定 `get()` 的"故障即未命中"契约，
  使 §1.1 的误判不会再次发生

### 2.5 影响与风险说明

| 维度 | 评估 |
|---|---|
| 类型 | 安全控制未遵守配置契约（过度保留），兼缓存陈旧风险 |
| 触发条件 | 任意以 `set()` 写入且 TTL < `CacheConfig::time_to_live` 的调用方 |
| 严重度 | **中**（不是越权，但会让锁定/凭据类状态超出配置时长存活） |
| 修复风险 | **中**：改为尊重 per-write TTL 会让所有短 TTL 条目的 L1 生命周期变短 → L1 命中率下降、L2 压力上升。已用全量测试评估（§5） |

## 3. 🟡 次要问题

### 3.1 配置开关作用于一条真实但较窄的路径

`login_lockout_fail_open_on_redis_error` 仅在图 `!cache.is_redis_enabled()` 分支生效
（`auth_compat.rs:355`），因为该分支是 `Err` 之外的**唯一**降级路径：

| 场景 | `is_redis_enabled()` | 行为 |
|---|---|---|
| 未配置 Redis | `false` | 按开关：`true` → 跳过检查；`false` → 503 |
| **配置了 Redis 但不可达** | **`true`** | **不进入该分支**；由 L1 层继续承担责任 |

⇒ 开关**并非死代码**（未配置 Redis 是真实场景，也是默认部署形态），
但它**无法用于"Redis 宕机时改为拒绝登录"**。若运维需要该语义，需要新增机制 —— 建议在 P5 明确文档化。

### 3.2 `privacy.rs::create_tables` 与权威 schema 漂移

`synapse-storage/src/privacy.rs:112-129` 的 `CREATE TABLE user_privacy_settings` **缺少**：

`profile_visibility`、`avatar_visibility`、`displayname_visibility`、`presence_visibility`、
`room_membership_visibility`、`allow_profile_lookup`、`allow_presence_lookup`、`allow_room_invites`

而 `privacy.rs:144` 的 `get_settings` 会 `SELECT ... profile_visibility ...`。
⇒ 经 `create_tables()` 建表的路径（测试 / `runtime-ddl`）执行 `get_settings` 会 SQL 报错。
生产走迁移路径不受影响。**移交 P3**（schema 单一真相源）。

### 3.3 `#[allow(dead_code)]` / `#[allow(unused*)]` 规模

全仓 **157 处**。本次抽查未发现被豁免的安全校验函数，但规模本身是 P5 的死代码债输入。

### 4.8 ✅ `unwrap_or(true)` 全量复核（44 处）

逐一判定，**未发现可达的 fail-open**：

| 类别 | 代表 | 判定 |
|---|---|---|
| 协议默认值 | `m.federate` 缺省 true（MSC 规定，`federation/signing.rs:178`） | ✅ |
| 语义为"无限制" | `allowed_rooms: None` → 允许（`secure_backup/service.rs:171`） | ✅ |
| 未配置即启用 | `is_dismissable`/`is_enabled` 等 DB 绑定默认 | ✅ |
| **曾疑为越权** | `visibility.get(uid).unwrap_or(true)` ×3（`directory_reporting.rs:94,154`、`friend_room.rs:651`） | ✅ **否证**，见下 |

**否证过程**（本次唯一需要深挖的候选）：
- 表面矛盾：单数版 `can_view_profile_for_requester` 用 `unwrap_or(false)`（fail-closed），
  复数版 `can_view_profile_for_requester_batch` 用 `unwrap_or(true)`（fail-open）——
  同一语义两处默认值相反，是典型的"可能被改错"信号。
- 追到 `synapse-storage/src/privacy.rs:286-327`：`batch_can_view_profile` **先为每个请求 user_id 插入 `true`**
  （`for uid in user_ids { result.insert(uid.clone(), true) }`），再用 DB 行覆盖
  ⇒ **保证返回 map 对每个请求 user 都有键**，`unwrap_or(true)` **不可达**。
- `user_privacy_settings.profile_visibility` 在权威 schema 中为 **`TEXT NOT NULL DEFAULT 'public'`**
  ⇒ `try_get::<String>` 失败分支（会退到 `allow_profile_lookup`）**不可达**。
- "查不到设置 → 默认可见"与 `DEFAULT 'public'` 及 Synapse 行为一致。

⇒ 两处默认值相反是"单数/复数语义不同"的合理结果，**不是漏洞**。
