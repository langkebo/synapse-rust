## 1. P1 · 备份存在，但**无 WAL 归档（无 PITR）**、无异地、无校验、无演练

> **⚠️ 更正记录（2026-10-15 同日）**：本节初版判定为 **P0「零备份」**，**该判定错误**。根因两条：
> ① 我用 `grep -rl "pg_dump\|pgbackrest\|…"` 检索，**`\|` 在 CLI 的 toybox grep 下静默返回空**
> （本项目已记录在案的坑，本轮又踩一次）；② 检索范围只覆盖 `*.sh/*.yml/*.rs`，**漏看 `docker/deploy/scripts/`**。
> 改用 Grep 工具复核后，实际存在 **两套备份脚本 + 一个配对恢复脚本 + 部署前自动备份**。
> 以下为复核后口径，**旧结论作废**（严重度 P0 → P1）。

**专业轨（事实与证据）**

| 检查项 | 实测结果 |
|---|---|
| WAL 归档 / PITR | ❌ `archive_mode=off`、`archive_library` 未设 ⇒ **无 PITR**，RPO = 距上次备份 |
| 备份脚本（dev） | ✅ `scripts/backup_database.sh`：`pg_dump -Fc -b` + Redis RDB，`KEEP_DAYS=7`，自带 `pg_restore` 恢复分支（:215） |
| 备份脚本（deploy） | ✅ `docker/deploy/scripts/backup.sh`（`set -euo pipefail`）：`compose exec -T postgres pg_dump … > database.sql` + media + `.env` + `config/` + compose，打 tar.gz，保留最近 5 个 |
| 恢复脚本 | ✅ `docker/deploy/scripts/restore.sh`（配对，`set -euo pipefail`） |
| 自动化程度 | ⚠️ **仅"部署前自动备份"**：`docker/deploy/deploy.sh:1788` `run_step "部署前备份" backup_current_state` → `./scripts/backup.sh`，包名存进 `ROLLBACK_BACKUP` 供回滚 |
| 周期调度 | ❌ 无 cron / systemd timer / compose 服务引用任一备份脚本（仅有注释里的 crontab 示例） |
| 备份落点 | ⚠️ dev 脚本默认 **`BACKUP_DIR=/tmp/backups`**（易失）；deploy 脚本默认 `./backups`（**与数据同机**） |
| 异地/离线副本 | ❌ 无（无 rclone / S3 / 对象存储） |
| 备份校验 | ❌ 两个脚本均**无** `pg_restore --list` / 校验和 / 行数比对 |
| 恢复演练证据 | ❌ 仓库内无演练记录 |

**两条最重要的具体缺陷**

1. **dev 脚本可能"静默产出空备份"**（且发生在**默认**路径上）：
   ```bash
   # scripts/backup_database.sh:20   → set -e（【无】pipefail）
   # scripts/backup_database.sh:105-113（默认 COMPRESS=true 分支）
   if docker exec "$PG_CONTAINER" pg_dump -U synapse -d synapse -Fc -b 2>/dev/null \
        | gzip >"$PG_BACKUP_COMPRESSED"; then
       log_success "PostgreSQL backup completed: …"    # ← 判的是 gzip 的退出码
   ```
   管道退出码取自**最后一个命令（gzip）**，`2>/dev/null` 吞掉 pg_dump 的报错，`if` 又屏蔽了 `set -e`；
   之后只 `du -h` 打印体积（:128），**不校验下限**。
   ⇒ 容器未起 / 认证失败 / 库名错等**任何** pg_dump 失败，都会得到"压缩成功的空文件 + SUCCESS 日志"。
   （对照：deploy 脚本有 `pipefail`，且用 `> database.sql` 重定向，**没有**此问题。）

2. **无 PITR + 无异地 ⇒ 主机/卷损毁仍等于"丢到上次备份"或"全量丢失"**：
   备份包与数据卷**同机**（`./backups` / `/tmp/backups`），一次主机故障同时带走两者。

**为什么仍列 P1（而非 P0）**：已有可用的备份/恢复**工具链**与**部署前自动备份**；
但 RPO/RTO **仍未成文**，"每次发布都有一次备份"与"每天都有备份"是两件事，
且"没演练过的备份等于没有备份"这条判据**未被满足**。

**修复（阶段 1）**
1. 定 RPO/RTO 并写进文档（自建单机建议：**RPO ≤ 15min、RTO ≤ 30min**）。
2. **补 WAL 归档**（唯一的 RPO 杠杆）：`archive_mode=on` + 外送（pgBackRest / WAL-G / `archive_command` + 对象存储）⇒ 获得 PITR。
3. **修 dev 脚本**：加 `set -o pipefail`；`pg_dump | gzip` 改重定向（或读 `PIPESTATUS[0]`）；加**最小体积下限**断言。
4. **备份异地**：`BACKUP_DIR` 指向数据卷之外的挂载/对象存储；改掉 `/tmp` 默认值。
5. **加廉价校验 + 恢复演练**：每次备份后 `pg_restore --list`；每季度恢复演练（临时实例 + 比对 `events`/`rooms` 行数），留档。
6. 接**备份新鲜度**告警（>26h 未成功备份即告警，与 §3 的 postgres_exporter 同批上）。

**验收**
```bash
# ① 归档在动（failed_count 必须为 0，archived_count 持续增长）
psql -c "SELECT archived_count, failed_count FROM pg_stat_archiver"
# ② 备份非空（修复 #3 的回归判据）
BACKUP_DIR=/var/backups ./scripts/backup_database.sh && ls -l /var/backups/synapse_pg_*.gz
# ③ 备份可读（廉价校验）
gunzip -c /var/backups/synapse_pg_*.gz | pg_restore --list | head
# ④ 停掉 PG 容器再跑一次：必须 FAIL 而不是 SUCCESS（变异自证，见方案 §B2）
```

**白话轨**：初版我说"一本抄本都没有"，**错了** —— 真实情况是**有抄本，但抄本和数据放在同一个房间**，
而且抄本**从没被翻开读过一次**（无校验、无演练）；更要紧的是抄本只在"搬家前"抄一次（部署前），平时不抄。
那台"抄写机"还有个坏毛病：没纸的时候会**交上一张白纸并盖章"已完成"**（pg_dump 失败仍记 SUCCESS）。
所以要办的正是四件事：抄本放**别的房间**（异地）、补**实时流水账**（WAL 归档 → 可回放到任意时刻）、
给抄写机加"**纸是空的就报错**"、以及**每季度真拿抄本重建一次**。

## 4. P1 · `pids_limit=256` 与 `max_connections=250` 不相容

**专业轨（实测推演，非估算）**

```
$ docker top synapse-postgres        # 空载时的常驻进程
postgres -c config_file=...          # 1  postmaster
postgres: logger                     # 1
postgres: checkpointer               # 1
postgres: background writer          # 1
postgres: walwriter                  # 1
postgres: autovacuum launcher        # 1
postgres: logical replication launcher   # 1
                                     # = 7 个非连接进程
```
再叠加 `max_worker_processes=8` / `max_parallel_workers=8`（实测）—— **并行 worker 也占 pid**。

⇒ 连接打满时：`250 + 7 = 257 > pids_limit=256`（并行查询时更多）。
表现是**连接被拒**（`could not fork new process for connection`），而**不是排队等待** ——
对客户端而言是"数据库突然拒绝连接"，极难归因。

现有门禁 `scripts/ci/check_connection_budget.py` 只校验**连接数**不变式
（`50 × 4 + 20 = 220 ≤ 250`，`docker/deploy/README.md` 成文表）——**不覆盖 pids，也不覆盖内存**。

**修复（二选一，阶段 1）**：
- A：`DB_PIDS_LIMIT` 提到 **≥300**（250 连接 + 7 常驻 + 8 并行 + 余量）；
- B：`max_connections` 降到 **≤240**，同步更新 `docker/deploy/README.md` 预算表（否则门禁红）。
建议 A（保留 4 进程 × 50 池的余量），并把 **pids 与内存**纳入 `check_connection_budget.py`。

> 需在你的宿主机上验证：cgroup v2 与 docker 版本对 `pids_limit` 的计数口径（含内核线程与否）。

**白话轨**：餐厅有 250 个座位、250 张椅子，但**门口只批了 256 个进人名额** —— 还有 7 个名额被"传菜员、收银、保安"（数据库的后台进程）常驻占着。座位坐满那天，第 250 位客人会被告知"满座"，而实际上**空着 7 个座位**。要么多批名额，要么少摆几张椅子。

## 5. P1 · 内存预算按最坏情况会打穿 `mem_limit`

**专业轨**

实测：`mem_limit=1536MB`、`shared_buffers=256MB`、`work_mem=16MB`、`maintenance_work_mem=64MB`；
空载 16 连接时容器内存 **108.2 MiB**（`docker stats`）。

风险的两条来源：
1. **`work_mem` 是"每排序/每哈希节点"上限**，不是每连接上限 ⇒ 理论最坏 `250 × 16MB = 4GB` 的瞬时内存，
   已远超 1536MB。真实值取决于并发复杂查询数量，但**没有任何护栏**（既无 `work_mem` 的
   per-role 限制，也无连接数-内存联合门禁）。
2. 每个后端进程有固定基线开销，250 个后端 + 并行 worker 的栈/哈希表开销未纳入预算。

后果特别严重的一点：**cgroup OOM 杀的是 postmaster** ⇒ 整库重启（所有连接断开），
而不是"杀一个慢查询"。这在无人值守时段就是一次真实宕机。

**修复（阶段 1，二选一或组合）**
- 按实测并发重算：`work_mem × 预期并发排序数 + shared_buffers + 后端基线 ≤ 0.8 × mem_limit`；
  经验起点：把 `work_mem` 降到 **4–8MB**、或把 `mem_limit` 提到 **2–2.5GB**；
- 对少数确实需要大 `work_mem` 的查询，用 `SET LOCAL work_mem` 逐语句放大，而不是全局放大。

> 需在你的 PG 版本/OS 上验证：具体并发排序数（`pg_stat_activity` 采样 + `log_temp_files` 观察），
> 本报告不臆造默认值。

**白话轨**：数据库的"案板"（`work_mem`）是按**每道菜**备料的，不是按**每位厨师**。现在厨房有 250 位厨师，每人切菜都按最大案板铺 —— 后厨面积（1536MB）根本放不下。真出事时，被赶出去的不是某位厨师，而是**整个后厨被掀掉**（OOM 杀 postmaster）。

## 6. P2 · 迁移器：无事务 + 容错模式无条件记成功 + 脚本路径无锁

> **2026-10-15 落地状态**（方案 B4，自证记录见 `DB_OPTIMIZATION_PLAN_…§13.8`）：
> 第 2 条（容错模式记成功）与第 3 条（shell 路径无锁）**已修**；第 4 条的"半建索引不可见"
> **已修**（升为 critical）。第 1 条（无事务 ⇒ 非原子）**保持现状**（9 条 `CONCURRENTLY` 决定），
> 其缓解手段是"失败不再静默 + 半迁移可被发现"；`§6.5` 的"热表排他锁 + 全表校验"**也已修**
> （B4.4：3 条 CHECK 改 `NOT VALID` + 独立 `VALIDATE`，排他锁窗口 603 ms → 6 ms，见方案 §13.9）。

**专业轨（逐条证据）**

1. **无事务、无原子性**：`docker/db_migrate.sh::apply_sql_file()` 执行
   `psql_db -v ON_ERROR_STOP=1 < "$file"` —— **未加 `--single-transaction`**。
   原因是必需的：基线里有 **9 条 `CREATE INDEX CONCURRENTLY`**（实测，行 5064–5338），
   它们不能在事务内执行。代价是**基线按语句自动提交**：中途失败 ⇒ **半应用的 schema 且无法回滚**。
2. ✅ **已修（2026-10-15，B4.1）**：~~容错模式无条件记成功~~
   ```bash
   if [ "$tolerant" = "true" ]; then
       psql_db <"$file" >/dev/null 2>&1 || true      # ← 错误被吞（原状）
       record_migration "$version" "$filename" ... TRUE ...   # ← 无论成败都记 true
   ```
   **实际修法**（方案原写的"按退出码"**不成立**：不带 `ON_ERROR_STOP` 时 psql 语句报错仍返回 0）：
   捕获 stderr、按其中 `^ERROR` 行数判成败，失败则记 `is_success=FALSE` 并 `return 1`
   （由既有的 `STOP_ON_MIGRATION_FAILURE` 决定是否阻断启动）；同时修掉 `init_database()` 里
   "调用后无条件 `return 0`"的吞错。
   半迁移**不再被永久固化**；"checksum 相同即 early return"这条路径现在只在**真的成功**后才走到。
3. ✅ **已修（2026-10-15，B4.2）**：~~shell 路径没有任何锁~~
   原状证据：Rust 运行时路径**有**会话级 advisory lock
   （`synapse-services/src/database_initializer/mod.rs`），而 shell 路径
   `grep -icE "advisory|flock|LOCK TABLE" docker/db_migrate.sh` = **0**。
   dev 栈在容器 entrypoint 跑 `db_migrate.sh`，deploy 栈用独立 `migrator` 服务 ——
   当前都是"单实例顺序"，但**一旦横向扩容或两条路径同时启动**，DDL 会交错（实测已能复现，见 §13.8）。
   现在 shell 与 Rust **取同一把** advisory lock（两侧都用同一条表达式
   `hashtext(COALESCE(current_database() || ':' || current_schema(), current_database() || ':'))` 派生 key，
   互加指认注释），由**一个长驻 psql 会话在整次 `migrate`/`init` 期间持锁**。
   ⚠️ 落地时发现：只锁"应用迁移文件"那段**覆盖不到记账阶段** —— 实测并发时后到者会撞
   `duplicate key value violates unique constraint "pg_type_typname_nsp_index"`（目录竞态）。
4. ✅ **已修（2026-10-15，B4.3）**：~~只查缺表/缺列，不查半建索引~~
   `schema_health_check.rs` 新增 `invalid_indexes`（`pg_index` 上 `NOT indisvalid OR NOT indisready`），
   非空即 `passed=false`，启动路径列为**致命**并给出 `DROP INDEX CONCURRENTLY` 线索。
   （`indisvalid=false` 时优化器不会用它；若是 UNIQUE 索引，**唯一性根本没被强制**。）
5. **附带风险（未修）**：`cleanup_stale_connections()` 会 `pg_terminate_backend` 掉
   `state='idle in transaction'` 且 >5min 的连接 —— 部署窗口内可能误杀应用的合法长事务。
   （本条 B4 未覆盖，维持登记。）

**修复（阶段 1–2）**
- ~~容错模式：按实际退出码记录~~ ⇒ **实测该判据不成立**，已按"`ERROR` 行数"实现（见上）；
- ✅ 已给 shell 路径加**与 Rust 侧同一把** advisory lock（key 用同一表达式派生）；
- 中期望：把 9 条 `CREATE INDEX CONCURRENTLY` 拆到**基线之外**的独立步骤，让基线本体可整体
  `--single-transaction`（换取原子性，代价是迁移清单从"1 个文件"变成"基线 + N 个索引步骤"）；
- ✅ 已把"半迁移"变成可发现状态：schema 健康检查增加"N 个 `INVALID` 索引"检测
  （`pg_index.indisvalid = false`，正是 `CONCURRENTLY` 失败后的残留形态）。

### 6.5 附带代价：基线"checksum 一变就整体重放"会在热表上产生排他锁 + 全表校验

`init_database()` 的既定行为：一旦基线的 checksum 与记录不符，就**重放整个基线**
（`docker/db_migrate.sh:502-507`）。而基线里有两类"重放代价随数据量增长"的语句：

| 语句形态 | 数量（实测） | 重放代价 |
|---|---|---|
| `ALTER TABLE … DROP CONSTRAINT IF EXISTS` + `ADD CONSTRAINT … CHECK` | **3 处**：`ck_rooms_room_id_format`（rooms）、`ck_events_event_id_format`（events）、`ck_room_memberships_valid`（room_memberships） | ⚠️ **原状**：`DROP` 取 **AccessExclusiveLock**（读写全阻塞）；`ADD CHECK` 需**全表扫描校验**、且在**同一把排他锁**下 ⇒ 表越大越久，期间**写入被阻塞**。**✅ 2026-10-15 已修（B4.4）**：`ADD … NOT VALID`（不扫表 ⇒ 排他锁窗口 ≈ 0）+ 同文件后段独立 `VALIDATE`（`ShareUpdateExclusiveLock`，不阻塞读写）。4,000,000 行实测：**603 ms → 6 ms**、被阻塞写 **3 → 0** |
| `CREATE INDEX CONCURRENTLY` | **9 条**（行 5064–5338） | 不长期阻塞写（这是选它的原因），但**失败会留下 INVALID 索引** —— ✅ 2026-10-15 起**已被检测**（B4.3：`invalid_indexes` 列为 critical，见 §6 第 4 条） |

前 3 处是**有意**用 DROP+ADD 而不是 `IF NOT EXISTS`（原文有理由：老库带着旧定义，只加不换会分叉；
`ADD CONSTRAINT` 也确实不支持 `IF NOT EXISTS`）—— **设计无误**，问题在**代价**：
`rooms` / `events` / `room_memberships` 都是核心表，`events` 是最大表。
⇒ **每一版 baseline 变更都会在这三张表上重跑一遍全表校验**，部署窗口 = 全表扫描时长 + 排他锁。

**结论（2026-10-15 实测，已落地为 B4.4；完整自证见方案 §13.9）**：

- ✅ 已给这三条 CHECK 改用 `ADD CONSTRAINT … NOT VALID` + 同文件后段的独立 `VALIDATE CONSTRAINT`；
- ⚠️ 本报告原先那句"`NOT VALID` 只取 `ShareUpdateExclusive`"**是错的**（已在上表更正）：
  实测**两种写法的 `ADD` 都取 `AccessExclusiveLock`**，`NOT VALID` 的作用只是**不扫表**；
  扫描由 `VALIDATE` 在 `ShareUpdateExclusiveLock` 下做 —— 那一步才不阻塞读写；
- ⚠️ **守卫盲区（已登记）**：模板路线**看不到** `NOT VALID` —— 隔离机制克隆用
  `CREATE TABLE … (LIKE … INCLUDING ALL)`，CHECK 在空克隆上被重建为 `convalidated=true`，
  所以 `monitoring::db_tests` 不能当这条的守卫（实测删掉 `VALIDATE` 后它仍通过）。
  建议给 `scripts/report_orphan_db_objects.py` 增一节"`NOT VALID` 的 CHECK"（须白名单排除
  `room_sticky_events` 那两条**有意**的 `NOT VALID`）；
- 仍未做（登记）：把这三条约束改成**只在定义变化时才 DROP+ADD**（用 `pg_get_constraintdef()` 比对当前定义）；
  以及部署 runbook 里写明"本次基线变更是否触及 `events` 的约束"。

**白话轨**：搬家具时是一个人一件件抬（不打包进一个箱子），好处是沙发太重也可以单独搬；坏处是**搬到一半被打断时，客厅是半搬状态**。更糟的是搬家记录写的是"已完成" —— 下次来的人看记录就以为搬完了。要么记录写实话，要么给门上加把锁，别让两个人同时搬。
再加一条：其中有一件家具（`events` 的约束）**每次搬家都要拆开重新验一遍全部零件**，家具越大，验得越久，期间**谁都不能动它**。

## 8. P3 · 重复索引守卫有覆盖盲区（含 `INCLUDE` 的重复对逃过检测）

**专业轨（实测）**

`scripts/check_baseline_consolidation.py::duplicate_indexes()` 报"无重复索引"，
但它的 `_INDEX_DEF_RE`（第 167-173 行）要求闭合括号后**只能**跟 `WHERE ...` 或 `;`：

```python
r"\((?P<cols>[^)]*)\)(?P<where>\s+WHERE\s+[^;]*)?;"
```

实测覆盖度：

```
守卫 _INDEX_DEF_RE 命中索引定义数 = 335
宽松正则命中索引定义数          = 343
⇒ 守卫漏掉 = 8 条
未覆盖名单：idx_users_lower_username / _lower_displayname / _lower_email（表达式索引，嵌套括号
           使 [^)]* 失配）、idx_events_sync_covering（INCLUDE）、idx_sliding_sync_{lists,tokens,rooms}_unique、
            idx_thread_replies_content_trgm（表达式 gin）
```

**正是这个盲区让一对真实重复索引逃过检测**：

```sql
-- migrations/00000000_unified_schema_v12.sql:3305 / 3307
CREATE INDEX idx_events_room_stream_ordering ON events(room_id, stream_ordering DESC);
CREATE INDEX idx_events_sync_covering        ON events(room_id, stream_ordering DESC)
                                             INCLUDE (event_id, sender, event_type, content, origin_server_ts);
```
两条**键列完全相同**，前者被后者在语义上包含 ⇒ 每次写 `events` 要维护两棵同键 B-tree，
而 `INCLUDE (…content…)` 让覆盖索引体积接近堆表 —— 实测 **21 MB vs 5.4 MB（heap 27 MB）**。

> ⚠️ **但不要据此删索引**：`DB_REVIEW_2026-09-17.md` §14.3 已用**真实计划**实测证明
> "两条都被真实代码路径选中"，裁定**两者都保留**。本节的问题**不是**"该删哪条"，
> 而是"守卫看不见这一对" —— 同类重复将来会继续静默进入基线。

**修复（阶段 2）**：修 `_INDEX_DEF_RE` 使其支持 ①嵌套括号（表达式索引）②`INCLUDE (...)` 子句；

## 12. P2 · 中文检索**当前完全不生效**（已实测确证，根因 = `datctype = C`）

> 本节初版只判到"2 字中文词可能失效"，属**低估**。实测发现是**整类查询失效**，故从 P3 升为 P2。

**专业轨（实测证据链，2026-10-15）**

| 探针 | `synapse` 库（现用） | `trgm_probe` 库（`LC_CTYPE='C.UTF-8'`，探针后已 DROP） |
|---|---|---|
| `datctype` | **`C`** | `C.UTF-8` |
| `show_trgm('北京')` | **`{}`（空集）** | `{iZG,0x8096b3,0xc9e4a4}` |
| `show_trgm('负载测试')` | — | `{0x2b483b,0x3b68fd,0x7db6e7,0xa9630e,0xb36d87}` |
| `'北京' ~ '[[:alpha:]]'` | `false` | `true` |
| `EXPLAIN … WHERE name ILIKE '%北京%'` | **Seq Scan**（7868 行全扫） | — |
| `EXPLAIN … WHERE name ILIKE '%Room%'` | **Bitmap Index Scan on `idx_rooms_name_trgm`** | — |

**同一张表、同一个索引、同一类查询，唯一差别是"查询串是中文还是 ASCII"** ⇒
中文模式无 trigram 可用 ⇒ 现有 9 个 `gin_trgm_ops` 索引对**纯中文列形同虚设**
（`idx_rooms_name_trgm`、`idx_rooms_canonical_alias_trgm`、`idx_spaces_{name,topic}_trgm`、
`idx_users_{username,displayname,user_id,email}_trgm`、`idx_thread_replies_content_trgm`），
而库里 `rooms` 有 **7,594 条中文名**（`name ~ '[一-龥]'`）——**代价已经在付，收益为零**。

**根因**：`POSTGRES_INITDB_ARGS: --encoding=UTF-8 --lc-collate=C --lc-ctype=C`
（`docker{,/deploy}/docker-compose.yml`）。C locale 下 `isalnum()` 对多字节 UTF-8 返回 false，
pg_trgm 遂把中文当**分隔符**剔除 ⇒ 索引无条目。
（`default_text_search_config = pg_catalog.english` 是**另一条**独立问题：FTS 对中文不切词。）

**修复路径（按成本排序，均需在你的 PG 版本/OS 上确认）**

1. **只改 `lc_ctype`、保留 `lc_collate=C`**：新建库 `LC_COLLATE='C' LC_CTYPE='C.UTF-8'` +
   dump/restore + **REINDEX**。探针已证明 alpine/musl **支持 `C.UTF-8`**（无需换基础镜像），
   这是唯一"不引入新扩展"的路子。
   - ⚠️ **改 ctype 会改变 `lower()`/`upper()` 对非 ASCII 的行为** ⇒ 基线里 3 个
     `lower(...)` 表达式索引（`idx_users_lower_{username,displayname,email}`）
     **必须 REINDEX**，否则索引与新语义不一致、查询会静默漏行。
   - ⚠️ 就地 `ALTER DATABASE … SET lc_ctype` 在 **libc provider** 上通常不可行 ⇒
     需走"新建库 + 迁移 + 重建索引"；**此条请在你的 PG 版本上确认，本报告不臆造**。
2. `pg_bigm`（bigram，1–2 字可用）或 `zhparser`（中文分词 + tsvector）：功能更贴中文，
   但要自建镜像/装扩展，并重做索引。
3. 应用层分词后入库（不改 DB，但检索语义与排名要自己维护）。

**判据（修完必须能复现的对照，而不是"看起来快了"）**
```sql
SELECT show_trgm('北京');                       -- 修复前 {}；修复后必须非空
EXPLAIN (ANALYZE, BUFFERS) SELECT room_id FROM rooms WHERE name ILIKE '%北京%';
-- 修复前：Seq Scan；修复后：Bitmap Index Scan on idx_rooms_name_trgm（且 REINDEX 已完成）
```

**白话轨**：图书馆的目录卡是"按三个字母一段"编的，而中文两个字组成一个词——**在现有 locale 下，
中文名字连一张卡片都没被编出来**（`show_trgm('北京')` 是空的），所以查中文只能把整个书架翻一遍。
不是"中文搜索慢"，是"中文这条通道根本没接上"。

### 16.2 根因：宿主 PG18 为什么会"自己又起来"

`/opt/homebrew/var/log/postgresql@18.log` 里的时间线（**证据级**）：

```
16:48:28 [36038] could not bind IPv4 "127.0.0.1": Address already in use → FATAL → database system is shut down
16:48:39 [36765] 同一失败（11 秒后重试）
16:48:49 [37461] 第三次抢到端口 → listening on 127.0.0.1:5432  ← 起来并稳定
17:06:18 [37461] received smart shutdown request            ← 这次停止同时移除了 launchd 作业 ⇒ 不再重启
```

对照 `/opt/homebrew/var/log/postgresql@15.log`：PG15 在 **16:48:39.719** 才输出
`database system is shut down`（即端口到那一刻才释放）。所以 PG18 的前两次尝试
（16:48:28 与 16:48:39.05）都撞在 PG15 的**关机窗口**上，第三次（16:48:49）才成功。

⇒ **"自己又启动"不是随机现象，而是 `brew services`（launchd）对 PG18 的 ~10 秒重试循环**：
每次进程因"端口被占"而 FATAL 退出，launchd 立刻再拉一次。**这也是"停了又在跑"的机制**。

### 16.7 口令强化：部署时生成强随机口令（同日收官）

§16.3 的临时方案把库口令对齐到 `synapse`，是弱值。整改做了四件事，每件都自证过。

| # | 改造 | 关键实现 | 自证（实测） |
|---|---|---|---|
| ① | **生成**：弱口令也当成"缺失"来补 | `generate-secrets.sh` 新增 `is_weak_password()`（弱口令名单 ＋ 长度下限 16）与 `maybe_set_password()`；`POSTGRES_PASSWORD` / `REDIS_PASSWORD` 改走它 | 8 个用例：`synapse` ⇒ 轮换为 32 字符；`CHANGE_ME` ⇒ 生成；强值 ⇒ 跳过（幂等）；`ALLOW_WEAK_DB_PASSWORD=1` ⇒ 保留并警告、`check-password` 返回 0；未放行 ⇒ 返回 1 |
| ② | **闸门**：弱口令拒绝部署 | `deploy.sh` 的 `check_env_file` 调 `./scripts/generate-secrets.sh check-password postgres`（判据**单一实现**，不另抄一份名单） | 弱值 ⇒ `exit 1`，并打印改强/放行两条命令 |
| ③ | **收敛**：口令落到**已有数据卷** | 新增 `converge_db_password()`：postgres 就绪后、**迁移之前**执行；先以 `.env` 口令走**非 loopback** 探测，不一致则 `ALTER ROLE`（口令经 psql 变量 `:'new_password'` 传入，避免引号/反斜杠破坏 SQL），再复验 | 四用例全过：失配 ⇒ 收敛成功；再跑 ⇒ "一致（无需收敛）"；正确口令 ⇒ `verify_database` 返回 0；**错口令 ⇒ 被判红** |
| ④ | **校验**：验证必须真的经过口令 | `verify_database()` 原实现是 `compose exec postgres psql -c "SELECT 1"` ⇒ 走容器内 `trust`，**口令错了照样通过**（而这正是 app 会踩的坑）。改为容器 IP ＋ 显式口令 | 见 ③ 的反例 |

**为什么探测必须走非 loopback**（容器 `pg_hba` 实测）：

```
local   all   all                  trust
host    all   all   127.0.0.1/32   trust
host    all   all   ::1/128        trust
host    all   all   all            scram-sha-256
```

⇒ 容器内 `127.0.0.1` 永远"通过"：**错误口令 ＋ loopback ⇒ 成功**；
**错误口令 ＋ 容器 IP ⇒ `password authentication failed`**；正确口令 ＋ 容器 IP ⇒ 成功。
（这就是"用 trust 路径验证口令等于没验证"的可复现证据。）

**工具链同步**（否则新口令会把测试/bench/报告工具静默打断）：新增
`scripts/lib/db_credentials.sh` 作为口令的**单一来源**（优先级：`DB_PASSWORD`/`TEST_DB_PASSWORD`
→ `docker/deploy/.env` 的 `POSTGRES_PASSWORD` → `docker/.env` 的 `DB_PASSWORD` → 兜底 `synapse`），
接入 11 个脚本与 `Makefile`：`init_test_public_schema` / `reset_database_v12` / `seed_test_db` /
`run_bench_server` / `cleanup_test_schemas` / `tune_test_db` / `ci_schema_health_check` /
`ci/{prepare_test_db, converge_public_schema, run_coverage, sliding_sync_perf_gate}`，
以及 `sqlx_prepare.sh` 的用法示例。**`docker/deploy` 与 CI 互不影响**：CI 没有
`docker/deploy/.env`，解析会落到兜底 `synapse`，与历史行为逐字一致。

**端到端实测**（改完立即跑，不是"改完就算完"）：

| 检查 | 结果 |
|---|---|
| 库口令 | **32 字符随机值**；宿主 `psql -h 127.0.0.1` 实测可连 |

**顺带修掉的既有缺陷**：

1. `generate-secrets.sh` 的 `update_env_file` 从 `sed -i` 改为纯 bash 重写 —— BSD 与 GNU 的 `-i`
   语义不同（`-i ''` vs `-i`），且在某些被包装的 shell 里 `-i ''` 会被当成文件名吃掉，实测报
   `sed: s|^A=.*|A=CHANGED|: No such file or directory`：于是"生成了密钥"的日志是真的、
   **写回 `.env` 却根本没发生**。重写版同时消掉了"值里含 `|` / `&` 时 sed 替换语义被吃掉"这一类问题。
2. `scripts/generate_env.sh` 一边生成随机 `SYNAPSE_DB_PASSWORD`、一边把 `DATABASE_URL` 写死成
   `synapse:synapse`（同一份输出里自相矛盾），已改为使用同一把随机口令；口令改用十六进制，
   避免 base64 的 `+` `/` `=` 嵌进 URL 需要百分号转义。
3. **`deploy.sh` 的日志门禁是"假绿"**：`verify_logs_clean` 用 `grep -Ei '\b(ERROR)\b'`，而 `\b`
   不属于 POSIX ERE —— GNU grep（CI）与 macOS BSD grep 支持，但 toybox / busybox 的某些构建会
   **静默失配**。实测（同一条含 `WARN`/`ERROR` 的样本）：`/usr/bin/grep -Ei '\b(ERROR)\b'` **命中**，
   而 PATH 更靠前的另一实现报"无匹配" ⇒ 这一步"分析容器日志"其实什么都没匹配到，却打印
   `SUCCESS`（`ERROR` 闸门与"未知 WARNING 默认阻断"**同时失效**）。改为 POSIX 字符类
   `(^|[^A-Za-z])(ERROR)([^A-Za-z]|$)` / `(^|[^A-Za-z])(WARN(ING)?)([^A-Za-z]|$)`，并新增
   `verify_log_filters_are_live()` **过滤器自检**（用必然含级别的样本证明匹配真的生效）。
   变异自证：把正则改回 `\b` ⇒ 自检**立刻判红**（旧实现此时是静默通过）；注入一条假 `ERROR`
   ⇒ `verify_logs_clean` 返回 1 并报 `失败步骤: verify-logs`。

   自检后在本机真实栈上跑：**已知=1、未知=0、无 ERROR ⇒ rc=0**。那 1 条已知告警是
   `Server-side Megolm rotation is not running`（`server.megolm_device_id` 未配置），
   **已在 `LOG_WARNING_ALLOWLIST` 里并附原因**（本项目 Megolm 按 Matrix 标准在客户端持有）
   —— 即"唯一的警告是预期状态"，不是本次口令变更引入的。

**刻意未做**：`TURN_SHARED_SECRET` 仍是 15 字符的短值（分析见文末复核命令块）。它与
`coturn` 的门配置耦合，轮换需要同时改两处并重启，属**独立变更**，不在本次数据库口令整改范围内 ——
登记为待办而不是顺手改掉。
