## 1. 冗余索引（写放大，零读收益）—— 最高优先级

10 组「同一张表、同一列、同一唯一性、同一方法」的**完全重复**索引。每一组都让
每次 INSERT/UPDATE/DELETE 多维护一棵 B-tree，而查询计划只会用到其中一棵：

| 表 | 列 | 重复的两个索引 |
|---|---|---|
| `account_data` | (user_id, data_type) | `idx_account_data_user_type` / `uq_account_data_user_type` |
| `device_lists_stream` | (stream_id) | `device_lists_stream_pkey` / `idx_device_lists_stream_stream_id` |
| `event_to_state_groups` | (event_id) | `pk_event_to_state_groups` / `idx_event_to_state_groups_event_id` |
| `e2ee_secret_storage_keys` | (key_id) | `e2ee_secret_storage_keys_key_id_key` / `idx_e2ee_secret_storage_keys_key_id` |
| `feature_flag_targets` | (flag_key, subject_type, subject_id) | `uq_feature_flag_targets` / `idx_feature_flag_targets_lookup` |
| `federation_access_stats` | (server_name) | `federation_access_stats_server_name_key` / `idx_federation_access_stats_server` |
| `federation_blacklist` | (server_name) | `uq_federation_blacklist_name` / `idx_federation_blacklist_server` |
| `federation_cache` | (key) | `federation_cache_key_key` / `idx_federation_cache_key` |
| `megolm_session_keys` | (user_id, session_id) | `uq_megolm_session_keys` / `idx_megolm_session_keys_lookup` |
| `megolm_sessions` | (session_id) | `uq_megolm_sessions_session` / `idx_megolm_sessions_session` |

**成因**：baseline 由历史增量迁移折叠而成，早期「先建索引、后补 UNIQUE 约束」的写法被原样保留
（折叠脚本 `check_baseline_consolidation.py` 只校验「增量对象是否已吸收」，**不检测对象重复**）。
**修法**：删掉每组的 `idx_*`，保留约束索引（`uq_*`/`pk_*`）。DDL 层面零风险（约束索引必存在）。

## 2. 前缀冗余索引（8 处）

短索引的列是同一张表另一索引的严格前缀 ⇒ 长索引可完整服务于短索引的等值/范围查询，
短索引只剩「体积小」这一个（通常不足以抵消写放大）：

- `key_signatures.idx_key_signatures_target` ⊂ `uq_key_signatures_signature`
- `space_hierarchy.idx_space_hierarchy_space` ⊂ `uq_space_hierarchy`
- `push_devices.idx_push_devices_user` ⊂ `uq_push_devices_user_device_pushkey`
- `device_lists_outbound_pokes.idx_device_lists_outbound_pokes_user` ⊂ `pk_device_lists_outbound_pokes`
- `device_keys.idx_device_keys_fallback` ⊂ `uq_device_keys_user_device_key`
- `room_memberships.idx_room_memberships_user_membership` ⊂ `idx_room_memberships_user_status`
- `sliding_sync_tokens.idx_sliding_sync_tokens_user` ⊂ `idx_sliding_sync_tokens_unique`
- `sliding_sync_lists.idx_sliding_sync_lists_user_device` ⊂ `idx_sliding_sync_lists_unique`

判定需人工确认：若短索引是为「更小的索引体积换更热的查询」而保留，应写注释说明；
否则删除。**注意**：`*_unique` 里含 `COALESCE(conn_id,'')` 表达式，PG 仍可用其前导列做前缀扫描。

> ⚠️ **2026-09-18 复核（Task 5，见 §14.3）**：这 8 个索引**全部仍在 baseline 中**
> ——即本节建议**一条都没执行**。其中两条经复核**不应按本节处理**：
> `device_keys.idx_device_keys_fallback` 是**部分索引**（谓词 `is_fallback AND NOT
> fallback_used`），不是长索引的严格前缀；`room_memberships.idx_room_memberships_user_membership`
> 被 `synapse-storage/src/schema_health_check.rs` 的 `REQUIRED_INDEXES` 列为必需索引，**删不得**。
> `room_memberships` 上 15 万合成行的实测显示规划器会在短索引 / 长索引 / 部分索引之间
> **按查询形状分别选择**，所以"前缀冗余"不等于"死对象"。原文保留作对照，**删除建议挂起**。

## 3. `events`（最热表）索引盘点：21 个

`public.events` 共 21 个索引（7 btree 全量 + 8 btree 部分 + 5 其他 + PK）。追加型最热表上
21 棵树意味着每次写事件都要维护 21 个索引——这是**写入路径的主要成本**。其中可确认的冗余：

- `idx_events_room_id (room_id)` —— 是 6 个以上索引的前缀 ⇒ 可删。
- `idx_events_room_stream_ordering (room_id, stream_ordering DESC)` —— 键与
  `idx_events_sync_covering (room_id, stream_ordering DESC) INCLUDE (...)` **完全相同**，
  后者是前者的覆盖版；两者并存属重复（保留覆盖版或保留小索引，二选一，需按同步查询的
  计划实测决定，别凭直觉）。

其余（`idx_events_not_redacted` / `idx_events_room_stream_ordering_not_redacted` /
`idx_events_friend_list` / `idx_events_friend_room` / `idx_events_room_soft_failed` /
`idx_events_state_dag_room`）都是**带 `WHERE` 的部分索引**，互不包含，属合理设计。

> ✅ **2026-09-18 实测结论（Task 5，见 §14.3）**：`idx_events_room_id` 已由 §12.1 删除
> （当前 baseline 中已不存在，实测 `WHERE room_id = ?` 由其它 room_id 前导索引接管）。
> `idx_events_room_stream_ordering` 与 `idx_events_sync_covering` 这**两个同键索引
> 本轮实测都被真实代码路径选中**，因此**两者都保留**（判定依据与 `EXPLAIN` 见 §14.3）。
> 本节"二选一"的建议**不采纳**。

## 4. 外键列缺少以它为前导的索引（18 个）

父行删除/更新时，PG 必须扫子表找引用行；无索引 ⇒ 每次级联删除退化为全表扫。
`ON DELETE CASCADE` 在这张表上会因此变慢并长时间持锁：

```
blocked_users.blocked_id          friend_categories.user_id      friends.friend_id
moderation_actions.user_id        notification_delivery_log.notification_id / .user_id
presence_subscriptions.target_id  qr_login_transactions.user_id  room_summary_update_queue.room_id
scheduled_notifications.notification_id  secure_backup_session_keys.backup_id
server_notices.user_id            user_directory.room_id         user_notification_status.notification_id
widget_permissions.user_id        widget_sessions.user_id / .widget_id   widgets.user_id
```

其中 `notification_delivery_log` 有 **两个** 未索引 FK（`notification_id`、`user_id`），
而它按设计是**写入型流水表**，最需要索引。

> ⚠️ **本节的 18 列清单已在 2026-09-18 逐行复核并证伪**（Task 5，见本文 §14.2）：
> §12.2 已给这 18 列各补一个前导索引并折入 baseline，**当前 baseline 中"无前导索引的
> 外键列 = 0"**；`moderation_actions.user_id` 所在的三张 `moderation_*` 表已在本轮
> 之前被删除（`15540350`），该行**整行失效**。此外本节清单本身**不完整**：
> 补索引前的本地库实测为 **27** 列（不是 18）。原文保留作对照，**不要**按本节去补索引。

## 5. 外键删除动作不一致

110 个 FK 中：**103 CASCADE、6 SET NULL、1 NO ACTION（默认）**。
唯一的例外：

```sql
-- events
fk_events_room FOREIGN KEY (room_id) REFERENCES rooms(room_id)   -- 无 ON DELETE
```

删除 room 时**必须**先删掉它全部 events（否则 FK 违约报错），与其他 103 个级联行为相反。
若这是刻意防误删，应显式写 `ON DELETE RESTRICT` 并加注释；否则应改为 CASCADE
（或按保留期清理流程处理），不应依赖默认值。

`access_tokens.device_id`、`module_execution_logs.module_id`、`notification_delivery_log.user_id`、
`refresh_token_families.device_id`、`refresh_tokens.device_id`、`registration_token_usage.token_id`、
`server_notices.user_id`、`token_blacklist.user_id`、`widgets.room_id`、
`worker_task_assignments.assigned_worker_id`。

> ⚠️ **`widgets.room_id` 是本节的过期读数**：本清单来自 v11 时代的本地库，baseline 早已是
> `NOT NULL`，Rust 侧也已在 §13.4.1 裁定并改齐（`Option<String>` → `String`）。

`server_notices.user_id` 这类**应为 NOT NULL** 的列建议收紧
（`server_notices` 是发给某用户的，`widgets` 属于某个房间——roomless widget 已裁定不合法，
见 §13.4.1，否则会出现「查不到归属」的脏数据）。

## 7. 类型与 DDL 卫生

- **PK 类型**：174 bigint / 45 text / **7 integer** / 3 uuid / 1 varchar(255)。
  7 张 `integer` PK 表（列名均为 `id`）：
  `device_lists_changes`、`room_ephemeral`、**`room_events`**、`room_tags`、
  **`search_index`**、`to_device_messages`、`user_filters`。
  其中 **`room_events`、`search_index`、`to_device_messages`、`device_lists_changes`、
  `room_ephemeral` 都是追加型高增长表**（`search_index` 是「每个被索引事件一行」）——
  int4 上限 21.4 亿，长期部署下这是**最现实的溢出/迁移风险点**，
  应在建库前就统一为 `bigint`（未发布项目，现在改代价最低）。
- **`SERIAL` 181 处、`IDENTITY` 0 处**：`SERIAL` 是遗留写法（隐式 sequence + DEFAULT + NOT NULL，
  且 sequence 所有权语义较弱）。功能无碍，但 `BIGSERIAL`/`SERIAL` 混用时容易出现
  上一条所述的类型意外。建议新表统一 `GENERATED BY DEFAULT AS IDENTITY`。
- ✅ **无 timestamp 列**（全 BIGINT 毫秒）——与代码约定一致，避免了时区/精度双重来源。
- **`VARCHAR(n)`**：31 个 255、2 个 50。`VARCHAR(n)` 的长度限制在 PG 里无性能收益，
  只在**业务确实要拒绝超长输入**时才有意义；若只是「随手写 255」，应改 `TEXT` 并让校验留在应用层
  （否则会出现「DB 报错、应用没校验」的 500）。
- **CHECK 约束 20 个 / 230 表**：覆盖率偏低，`status`、`*_type`、布尔语义列基本靠应用层自律。

## 8. JSONB 索引覆盖

108 个 jsonb 列，仅 25 个 GIN 索引。对**只整列读写**的 payload（如 `event_json`、`content`）无碍；
但凡做 `@>` / `?` / `->>` 过滤且无 GIN 的列都会全表扫。建议对已知热点
（`push_rules.actions`、`room_summaries` 的统计块、`federation_cache` 的响应体）逐列确认是否有
containment 查询；`idx_events_content_gin` 用 `jsonb_path_ops` 是正确选择（比默认 `jsonb_ops` 小且快）。

## 9. 运行参数与容量

- 本机 `max_connections = 100`，应用配置默认 `max_size = 20`（`synapse-common/src/config/database.rs`）。
  按 100 计算：**最多 5 个进程**（1 个主进程 + 4 个 worker/测试进程）就会打满；测试并行时
  会直接 starvation（仓库历史上有「1417 passed / 12 failed+7 timeout」的记录，根因即此）。
  建议：要么把 `max_connections` 提到 ≥200，要么在文档/启动检查里锁死
  `pool_size × 进程数 + 测试进程数 ≤ max_connections` 的不变式（当前无此门禁）。
- **0 张分区表**：`events`、`device_lists_stream`、`to_device_messages`、`presence`、
  `notification_delivery_log`、`audit_events` 都是**只增不减**型，长期部署必然需要
  保留期清理 + 分区。现有清理走 `RetentionService`/`prune_*` 脚本（应用层删除），
  删除大表历史数据会产生大量 dead tuple 与 autovacuum 压力，**分区（按月/按 stream 区间）+
  DROP PARTITION 才是结构性解法**。这是本报告中**唯一需要架构级投入**的项。

# 11. 落地记录与两处更正（2026-09-17 执行）

## 11.1 更正一：重复索引是 **28 组**，不是 10 组
§1 的清单来自一条带 `limit 10` 的查询，**被截断了**。落地时在干净库上重新枚举，
实际为 **28 组**（另外 18 组：`federation_queue`、`oidc_auth_sessions`、
`registration_captcha`、`report_rate_limits`、`room_aliases`、`room_invite_allowlist`、
`room_invite_blocklist`、`room_memberships`×2、`room_summaries`、`room_summary_members`、
`space_summaries`、`state_group_state`、`threepid_validation_session`×3、
`upload_chunks`、`user_threepids`）。**§1 的"10 组"应以本节为准**，结论方向不变。
教训：报"共 N 条"之前必须确认查询没有 `limit`。

## 11.2 更正二：§5 的"不一致"其实是**同一列上的重复外键**，且它是真缺陷
§5 把 `fk_events_room` 的 `NO ACTION` 描述为"与其他 103 个 CASCADE 不一致，建议改成 CASCADE"。
**这个建议是错的，落地前的代码核查推翻了它**：

- `RoomStorage::delete_room`（`synapse-storage/src/room/mod.rs`，DB-04-b）**故意**先按 1000 行
  分批删除 events，最后才删 rooms 行 —— 因为 CASCADE 会在整张 `events` 表上取
  `AccessExclusiveLock`，阻塞该表所有并发读写。`NO ACTION` 在这里是**最终校验手段**。
- 真正的问题是**同一列上存在第二个外键**：表级 `fk_events_room`（NO ACTION）之外，
  baseline 尾部的 DO 块又加了 `fk_events_room_id ... ON DELETE CASCADE`
  （该 DO 块只检查自己的名字是否存在，因此不会与内联约束冲突而被跳过）。
- 后果两条：① CASCADE 仍然会触发，DB-04-b 想避免的表级锁照样发生；
  ② 代码末尾的 `DELETE FROM rooms` 会**静默成功**（残留 events 被级联删掉），
  "events 已删净"的校验形同虚设。
- 该缺陷**早已被记录**：`docs/audit/PROJECT_ACTUAL_ISSUES_2026-09-14.md:1370-1378`
  （"`fk_events_room_id` | **CASCADE** | 后面的 DO 块 … 两个都在"），只是从未修。

**同类缺陷共 6 处**（不止 events 一处）：`access_tokens.user_id`、`devices.user_id`、
`refresh_tokens.user_id`、`room_memberships.room_id`、`room_memberships.user_id`
各有 `fk_<table>_<col>` 与 `fk_<table>_<col>_id` 两个外键，两侧动作**都是 CASCADE**
（即删除冗余那个不影响行为）。全部 6 处已删除重复的那个，保留内联约束。

# 12. 优先级 2 / 4 / 5 / 7 / 8 的处理（2026-09-17 续）

## 12.1 优先级 2（events 索引取舍）—— 拆成"可安全做"与"必须先测量"两半
- **已做**：删除 `idx_events_room_id (room_id)`。`room_id` 是 ≥6 个其它索引的**前导列**，
  纯前缀冗余：`WHERE room_id = ?` 用任何一个复合索引的 btree 下降路径都同样高效。
- **未做（需实测）**：`idx_events_room_stream_ordering (room_id, stream_ordering DESC)`
  与 `idx_events_sync_covering (room_id, stream_ordering DESC) INCLUDE (event_id, sender,
  event_type, content, origin_server_ts)` **键完全相同**。二者各有理由：覆盖索引支持
  index-only scan（大表上省 heap 访问），但 `INCLUDE (content)` 让它**接近堆表大小**；
  非覆盖索引小得多，凡是要回表读内容的计划反而更省页。**取舍取决于真实数据分布与
  同步查询的实际计划，不能用元数据判断**（本轮已因"凭元数据下结论"栽过一次，见 §11.2）。
  测量方法（生产镜像上跑）：
  ```sql
  -- 1) 覆盖索引的真实体积与占比
  SELECT pg_size_pretty(pg_relation_size('idx_events_sync_covering')) AS covering,
         pg_size_pretty(pg_relation_size('idx_events_room_stream_ordering')) AS plain,
         pg_size_pretty(pg_relation_size('events')) AS heap;
  -- 2) 同步查询在两种索引下的计划与缓冲命中（分别 DROP 一个再跑，或用 pg_hint_plan 强制）
  EXPLAIN (ANALYZE, BUFFERS) SELECT event_id, sender, event_type, content, origin_server_ts
  FROM events WHERE room_id = $1 AND stream_ordering > $2 ORDER BY stream_ordering DESC LIMIT 50;
  ```
  判据：若典型同步查询能走 index-only scan 且 covering 体积可接受 → 删 non-covering；
  若多数计划仍需回表（或 covering 已接近堆表大小）→ 删 covering、保留小索引。

## 12.5 优先级 8（追加型大表分区）—— **本轮不实现**，给方案与判据
不实现的三条理由，按重要性排序：
1. **会牵动主键**：PostgreSQL 的声明式分区要求**分区键必须包含在每个唯一索引/主键里**。
   `events` 的主键是 `event_id`（无分区键），要按 `origin_server_ts` 或 `room_id` 分区，
   就必须把 PK 改成 `(event_id, <分区键>)` 或 `(<分区键>, event_id)` —— 这会改变
   `ON CONFLICT`/去重语义与所有 `WHERE event_id = ?` 的计划，属**语义级**改动。
2. **应用侧不是透明的**：`synapse-storage` 里大量查询按 `room_id`/`stream_ordering`
   跨分区扫描；分区后需要保证分区裁剪条件出现在谓词里，否则计划退化为扫所有分区
   （比现在更慢）。这需要逐个热点查询审一遍。
3. **当前无数据、无生产**：分区的收益（DROP PARTITION 代替百万行 DELETE + vacuum）只在
   有量级数据时才成立；在空库上"先把结构布好"会把上述 1、2 的风险提前兑现而拿不到收益。

**建议的落地顺序**（真正需要时）：先只对**保留期最明确**的 `to_device_messages`
做试点（它按 `created_ts` 单调增长、查询几乎都带 `recipient` + 时间窗），
用「按月 RANGE 分区 + 保留 N 个月 → `DROP PARTITION`」跑通清理路径，
再评估 `events` / `device_lists_stream` / `audit_events`。
**在此之前**，应先确认现有清理路径是否真的在跑（`RetentionService` 的
`run_data_lifecycle_cycle`、`prune_*` 脚本）——若 pruning 未启用，分区只是把同样的问题
推后，而不是解决它。

## 13.6 两个**未修**的既有缺陷（需裁定 / 另案）

### 13.6.1 集成测试**静默假绿**：schema 克隆失败被吞（严重）✅ 已修（commit `758003dc`）

**机制**：`tests/integration/mod.rs:462` 用
`synapse_test_utils::acquire_pooled_schema().await.ok()?` 取隔离 schema；失败即
`TestContext::new()` 返回 `None`，而调用方一律是
`let Some(app) = setup_test_app().await else { return; };` —— **测试直接"通过"**。
错误被完全吞掉（`RUST_LOG=debug` 全量日志里一条 ERROR/WARN 都没有）。

**实测根因**（把 `.ok()?` 换成打印错误的探针后）：

```
clone of test_63297_1_... from test_template_v2_a2fc82a87d9e59c7 failed:
error returned from database: permission denied for language c
```

模板 schema 里装着 `pgcrypto`，克隆逻辑用 `pg_get_functiondef` **逐条重放函数**，
其中 `digest/hmac/crypt/...` 是 `LANGUAGE c` 的扩展函数；`synapse` 角色
`rolsuper = f`（本机 Homebrew PG，`ljf` 才是超级用户），于是重放被拒。
超级用户下克隆成功、测试才真正执行 —— 这正是本轮 19/19 与"假绿 19/19"的区别。

**修法（已实施）**：

1. 克隆时**不重放扩展所属函数**（判据
   `NOT EXISTS (SELECT 1 FROM pg_depend d WHERE d.objid = p.oid AND d.classid = 'pg_proc'::regclass AND d.deptype = 'e')`），
   并把 `validate_clone` 的函数计数改为**同一判据**（否则"不克隆"与"要求存在"自相矛盾，
   实测报 `functions 7/43` 判克隆不完整）。
2. `pgcrypto` 与 `pg_trgm` 一起**钉进 `public`**（`pin_public_extensions()`，顺带把三处
   重复的 pg_trgm 固定逻辑收敛为一份），因为克隆的 `search_path` 是
   `<clone>, public`，扩展在 public 才可按名解析；失败时**大声告警**而非静默 `let _ =`。
3. `.ok()?` 的静默吞错改为：`None` **只**表示"没有测试库"（进程内解析一次），
   **建库失败一律 panic**。

⚠️ **上面第 527-529 行的原建议是错的**（已作废并保留在此以便对照）：PostgreSQL 扩展是
**库级**对象，一个库只能有一份 `pgcrypto`；在克隆 schema 内 `CREATE EXTENSION` 会是
no-op，而 `ALTER EXTENSION ... SET SCHEMA` 会把唯一实例**从模板移走**、破坏所有其他克隆。
而且 `ALTER EXTENSION` 需要**成员对象**的 owner —— 实测
`must be owner of function digest`（扩展本身属 `synapse`，但成员属于最初安装它的 `ljf`）。

**实测结果**：`synapse` 角色 `rolsuper = false` 时
`cargo test --test integration --all-features worker_body` ⇒ **3 passed**、
耗时 4.50s 且断言真实执行（此前是每次 ~0.4s 的"克隆失败→空转跳过"）。
本轮用它取得真实证据后**已还原**。

### S3 SAS MAC 永不校验 ✅ 已修（**是"停止伪装"，不是"补上校验"**）

**必须准确表述**：审计的判断（"任何参与者发任意 mac 即置 Done"）在**代码行为上成立**，
但**这不是可以通过服务端修好的漏洞** —— SAS MAC 是以 SAS 共享密钥为密钥、对各自
own 的 key 做 HMAC，**只有两端客户端能验**；服务端拿不到 SAS 密钥，且两端 MAC 本来
就不同（各覆盖自己那侧的 key）。所以"服务端比对 MAC"在密码学上不成立。

真实缺陷是**伪装**：`confirm_sas` 里
`if let Some(stored_mac) = &sas_state.mac { mac_matches(...) }` 永远不会进入
（生产路径**三处** `store_sas_state` 调用——`service.rs:159`、`:217`、`:262`——写入的
`SasState` 都是 `mac: None`：前两处分别在 `:145-157`、`:196-208` 显式构造，第三处复用
前两处写回的状态），而一个名为
`confirm_sas_rejects_wrong_mac_and_cancels_transaction` 的测试**只断言 `mac_matches`
本身**，从未调用 `confirm_sas` —— 这正是"以为 MAC 校验在工作"的假信心来源。

**修法**：①删除该分支（不可达，且若可达会因比对两个本应不同的值而**误取消**合法验证）；
②删除只服务于它的 `mac_matches` 及其 4 个单元测试；③删除那个名不副实的测试；
④顺带删除同一文件里恒真断言 `assert!(!"m.sas.v1".is_empty())` 的
`generate_qr_code_produces_valid_data_structure`；⑤就地写明信任边界（客户端才是
`m.key.verification.mac` 的信任边界），并保留"mac 非空"的协议形状校验。

**遗留**：`VerificationState::Done` 仍是**调用方客户端所断言**的事实。若要在服务端
增加实质约束，可行方向是要求"双方都提交过 MAC"（状态/存活检查，需要迁移加列），
那属于功能开发，不是本条的修复。

### S4 `Forwarded: for="` 触发未鉴权 panic ✅ 已修

`parse_forwarded_for` 用 `starts_with('"') && ends_with('"')` 判引号，而**单个引号字符
同时满足两端**，于是 `&original[1..len-1]` 变成 `&s[1..0]` → panic；
`extract_client_ip` 在 `peer_addr == None` 时无条件解析该头，而
`admin_auth_middleware` 正是传 `None` ⇒ 未鉴权远程 DoS。
**修法**：改用 `strip_prefix('"').and_then(|s| s.strip_suffix('"'))`（长度 <2 时自然
不匹配）。
**证明**（独立 `rustc` 编译复刻两版逻辑，不依赖工作区编译）：
修前 `"` → **PANIC**、`""`→`""`、`"""`→`"`、`"192.0.2.60"`→`192.0.2.60`；
修后 `"` → 原样返回，其余不变。并新增两个回归测试
（`forwarded_header_with_lone_quote_does_not_panic`、
`forwarded_header_quoted_value_is_unwrapped`）。

**结论**：A1 修好"假绿"的直接代价就是**一次性暴露 80 条既有失败**。这是好消息 ——

## 15.8 合并后独立复核发现：清理脚本的"硬排除"在无标记路径下是空的（2026-09-19 已修）

本节记录的是**合并之后**为了给本地环境做卫生（重播 `migrations/` + 清理残留测试 schema）
而运行 `scripts/cleanup_test_schemas.sh` 时暴露的问题 —— 属"门禁必须能变红"（铁律 8）与
"同一职责一份判据"（铁律 2）那一类，不是本轮 Task 1–8 引入的。

### 15.8.1 事实与证据

`scripts/cleanup_test_schemas.sh` 的注释自称有一条 **HARD EXCLUSION**，用于保护
`test_template_ci`（CI 各测试步骤 `TEST_DB_TEMPLATE_SCHEMA: test_template_ci` 钉住的共享模板，
由 `scripts/ci/prepare_test_db.sh` 以纯 shell 创建，**没有** Rust 就绪标记文件）。矛盾在于：

- 该硬排除写作 `KEEP_EXCLUDE="AND nspname NOT IN ($KEEP_SQL)"`，而 `KEEP_SQL` **仅在**
  keep 集合非空时才有值；keep 集合来自 ①标记文件 ②`TEST_DB_TEMPLATE_SCHEMA` ③`--keep-template`。
- 在**最常见的本地路径**（新 `CARGO_TARGET_DIR` 无标记、shell 未导出 `TEST_DB_TEMPLATE_SCHEMA`）
  三者皆无 ⇒ 脚本降级为 `KEEP_ALL_TEMPLATES=1`，同时 `KEEP_SQL` 为空 ⇒ 硬排除子句**整体消失**。
- 而 `test_template_ci` 只匹配 `test\_%`，**不**匹配两个指纹家族正则
  （`^test_template_v<N>_<hex>$`、`^test_isolation_template_<hex>$`），所以候选谓词救不了它。

实测（`synapse_test`，2026-09-19）：

```console
$ env -u TEST_DB_TEMPLATE_SCHEMA SYNAPSE_TEMPLATE_MARKER_DIR=/nonexistent-marker-dir \
    DATABASE_URL=postgresql://synapse:synapse@localhost:5432/synapse_test \
    bash scripts/cleanup_test_schemas.sh          # 修复前
WARN: 找不到任何 live 模板标记（/nonexistent-marker-dir），且未设 TEST_DB_TEMPLATE_SCHEMA。
      为避免误删仍在使用的模板，降级为「保留全部模板家族、仅清理克隆 schema」。

    test_template_ci                              ← 真正的 --apply 会 CASCADE 掉它
```

后果：`AGENTS.md` 把"测试 schema 残留"的解法指向本脚本，运维照做时若未导出
`TEST_DB_TEMPLATE_SCHEMA`（本地常态），就会删掉 CI 依赖的共享模板；克隆的列默认值引用模板序列
（`LIKE ... INCLUDING ALL` 复制的是 DEFAULT 表达式），CASCADE 还会连带破坏并发克隆。

`docs/audit/PROJECT_REMAINING_ISSUES_2026-09-14.md`（§2 第 557-558 行）当时声称
"`test_template_ci` 等明确 live 模板**绝对安全**"、"TEST_DB_TEMPLATE_SCHEMA 独立保护" ——
后半句只在该变量被导出的前提下成立，前半句在本地路径下不成立。该文档为**历史快照，保留不改**。

### 15.8.2 修复

- 新增**静态** live 模板名单 `STATIC_KEEP=("test_template_ci")`：名字固定、由 shell/CI 创建、

- 运行时会打印 `==> 静态保护的 live 模板（无条件硬排除）: test_template_ci`，便于运维核对
  "为什么这个模板没被清理"。
- `tests/unit/cleanup_schema_script_tests.rs` 新增守卫
  `cleanup_script_hard_excludes_static_live_templates_without_markers`（钉住静态名单存在、
  `KEEP_EXCLUDE` 单次无条件赋值、排除子句以 `$STATIC_KEEP_SQL` 开头、空名单 fail-loud）；

## 15.9 D3 落地：数据库就绪探针的"假健康"，外加一个死的第三迁移入口（2026-09-19）

§15.3 的 D3 原本只记了两句："`migrator` 为 `restart: \"no\"`，且 `pg_isready` 可能在
initdb 临时实例上先通过（假健康）"。落地时把两半都做实了，并在同一片区域又发现两个问题。

### 15.9.1 机制与实测

官方 `postgres` 镜像的 entrypoint 在 initdb + `docker-entrypoint-initdb.d` 阶段先起一个
**只监听 unix socket** 的临时实例（`-c listen_addresses=''`）。因此不带 `-h` 的
`pg_isready -U <user> -d <db>` 会在**初始化中途**返回 `accepting connections`（exit 0），
容器被判 healthy；而 `pg_isready` 的退出码**本就不校验**用户/库/密码是否可用。

后果（两个栈都有）：

- deploy 栈：`depends_on: condition: service_healthy` **与** `deploy.sh` 的
  `wait_for_container_health synapse-postgres` 一起过早放行 migrator，而 migrator 走 TCP；
  它自己的重试窗口只有 `retry 3 5`（约 10s），慢机器上初始化更久 ⇒ 部署以
  "数据库迁移失败"中止。
- dev/CI 栈：`synapse-rust` 的 entrypoint 迁移与 `backend-validation` 同样会提前启动。

实测（2026-09-19，全新 `postgres:16-alpine`，init 脚本仅 `SELECT pg_sleep(30)`）：

```console
t=8s  OLD(no -h,unix) rc=0 /var/run/postgresql:5432 - accepting connections | NEW(TCP+auth) rc=2
t=16s OLD(no -h,unix) rc=0 /var/run/postgresql:5432 - accepting connections | NEW(TCP+auth) rc=2
t=24s OLD(no -h,unix) rc=0 /var/run/postgresql:5432 - accepting connections | NEW(TCP+auth) rc=2
t=32s OLD(no -h,unix) rc=0 …                                              | NEW(TCP+auth) rc=2
（真实实例起来后）NEW rc=0，输出 `1`；OLD 同样 rc=0
```

即**旧探针连续 24s+ 报健康，新探针同时段全部失败**，只有真实例就绪后两者才一致。

再用 **docker 自己的 health 引擎**跑一遍两个容器（同一份慢初始化，`--health-interval 4s`），
这是端到端口径 —— 不只是命令返回值，而是 `docker inspect .State.Health.Status`：

```console
t=12s OLD_BARE=healthy  NEW_TCP_AUTH=starting      ← 旧探针在 init 中途就 healthy
t=28s OLD_BARE=healthy  NEW_TCP_AUTH=starting
t=32s OLD_BARE=healthy  NEW_TCP_AUTH=healthy       ← 新探针等真实例就绪
$ docker inspect … hc_new → 0: 127.0.0.1:5432 - accepting connections / 1   ← 查询真的执行了
```

顺带一个**测试自身的教训**：首次跑这个对照时新探针一直 `starting`，原因是我的临时容器
只设了 `POSTGRES_PASSWORD`/`POSTGRES_DB`、**没设 `POSTGRES_USER`**，于是 psql 落到
OS 用户并报 `FATAL: role "root" does not exist`（`pg_isready` 那半仍 rc=0，因为它不校验用户）。
两个 compose 栈都在 `environment:` 里显式设了 `POSTGRES_USER`，故配置本身没问题；
但这也说明探针**没静默失败**：变量缺失时它会一直不健康（失败方向安全），而不是假健康。

### 15.9.2 修复

- `docker/deploy/docker-compose.yml` 与 `docker/docker-compose.yml` 的 postgres/db
  healthcheck 改为"**TCP + 一次真实认证查询**"：
  `pg_isready -h 127.0.0.1 -p 5432 -U "$POSTGRES_USER" -d "$POSTGRES_DB" && PGPASSWORD="$POSTGRES_PASSWORD" psql -h 127.0.0.1 … -tAc 'SELECT 1'`
  —— 这才等于 migrator 真正需要的语义（该用户名/库能连、能查）。`start_period: 20s`
  让初始化期间的失败不计入 `retries`，方向正确，保留。
  已实测 compose 转义正确：`docker inspect` 显示容器收到的是 `"${POSTGRES_USER}"`（而非字面 `$$`），
  容器内展开为真实用户名。
- `migrator.restart`：`"no"` → `"on-failure:3"`。注意 `deploy.sh` 走 `compose run --rm`，
  而 `run` **不套用** restart 策略 ⇒ 本项不影响标准部署路径；它兜住直接
  `docker compose up` 起整栈的用法（原先一次瞬时失败会把栈留在"服务起来了、schema 没迁移"）。
  重试 3 次仍失败照样停止，不掩盖真错。
