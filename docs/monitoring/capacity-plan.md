## 2. 容量估算模型

### 2.1 TSDB 存储估算

```
公式：
  每天存储 = 指标数 × (86400 / 采集间隔) × 每点开销 × 冗余系数

参数：
  指标数：~222（含 bucket 展开）
  采集间隔：15s
  每点开销：~100 bytes（含 label 元数据、索引、WAL）
  冗余系数：10（实际开销远超原始数据）

计算：
  每天 = 222 × 5760 × 100 × 10 / (1024^3) ≈ 1.2 GB/天
  30 天 = 36 GB
```

### 2.2 内存估算

```
Prometheus 内存 = 样本缓冲 + WAL + 索引 + 查询缓存

参数：
  活跃序列：~222
  每序列内存：~4 KB
  WAL 缓冲区：~500 MB
  查询缓存：~200 MB

计算：
  总内存 ≈ 222 × 4KB + 500MB + 200MB ≈ 1.4 GB
  建议配置：1 GB（实测 ~800 MB 稳态）
```

### 2.3 CPU 估算

```
Prometheus CPU = 抓取 + 写入 + 查询

参数：
  抓取：6 目标 × 每 15s → ~0.5 CPU
  WAL 同步：~0.2 CPU
  查询（Grafana 面板）：~0.3 CPU

总计：~1.0 CPU
```

## 4. 容量阈值与告警

### 4.1 磁盘容量

| 阈值 | 条件 | 操作 |
|------|------|------|
| 警告 | > 70% 使用 | 检查 retention，评估扩展 |
| 临界 | > 90% 使用 | 降低 retention.size 或扩容 |
| 紧急 | > 95% 使用 | 立即删除旧数据 + 扩容 |

### 4.2 内存容量

| 阈值 | 条件 | 操作 |
|------|------|------|
| 警告 | > 800 MB | 检查是否有 OOM 倾向 |
| 临界 | > 1 GB | 增加内存限制 |

### 4.3 时间序列数量

| 阈值 | 条件 | 操作 |
|------|------|------|
| 警告 | > 50,000 | 检查是否有高频指标泄漏 |
| 临界 | > 100,000 | 降采样或拆分 |

## 5. 容量扩展方案

### 5.1 短期（1-3 个月）

当前配置可支撑，无需扩容。

### 5.2 中期（3-6 个月）

如指标增长到 300+ 条：

```yaml
# docker-compose.monitoring.yml 调整
prometheus:
  command:
    - '--storage.tsdb.retention.size=50GB'  # 从 30d 改为 size 限制
    - '--storage.tsdb.min-block-duration=2h'  # 降低 compaction 频率
  mem_limit: 2g  # 从 1g 提升到 2g
```

### 5.3 长期（6 个月+）

如指标增长到 500+ 条或需要 HA：

- 方案 A：VictoriaMetrics 单节点（更低内存 + 更好压缩）
- 方案 B：Prometheus 双副本 + 共享存储
- 方案 C：Mimir / Cortex（多租户 + 长期存储）

## 6. 备份策略

### 6.1 快照备份

```bash
# 每日快照
0 2 * * * curl -s -X POST http://localhost:9092/api/v1/admin/tsdb/snapshot

# 快照保留 7 天
find /backup/prometheus/ -name 'snapshot-*' -mtime +7 -delete
```

### 6.2 远程归档

```bash
# 快照后上传到对象存储
aws s3 cp /backup/prometheus/ s3://backups/prometheus/ --recursive
```
