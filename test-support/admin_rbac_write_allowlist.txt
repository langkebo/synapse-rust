# 普通 admin 角色**可以**调用的 admin 写路由（显式登记表）。
#
# 为什么需要这份清单：`is_role_allowed("admin", …)` 的允许面是一条按前缀的 OR 链
# （`/_synapse/admin/v1/users`、`/rooms`、`/media` …），黑名单只从里面挖掉一些洞。
# 于是**任何新增的、落在这些前缀下的写端点都会自动对普通 admin 开放**，没有任何
# 东西会提醒你。本清单把它变成显式声明：`admin_rbac_tests` 断言
# 「普通 admin 可执行的写路由」与「本文件」**双向相等** ——
#   · 新增端点落进前缀但没登记 ⇒ 测试红；
#   · 登记了但已不再可执行（规则收紧/路由删除）⇒ 测试红。
#
# 登记一条之前先问：这个写操作给普通 admin 合理吗？不合理就把它加进
# `is_super_admin_only_endpoint`，而不是登记到这里。
#
# 格式：`<METHOD> <path>`，`#` 开头为注释。路径用 ROUTE_HANDLERS.json 的原样形式。

# --- device_verify ---
# 交叉签名单设备验证。**登记为可执行是刻意的**：`allowlist.rs` 的
# `AdminRoute::UserDevices` 规则本来就把「/users/<id>/devices… 下的单设备操作」
# 整体划给普通 admin（只排除 `…/delete` 批量删除），所以这条路由一落地就对普通
# admin 开放，本清单要求把它显式记下来。
#
# 为什么不该收紧成超管专属：同一前缀下普通 admin **已经可以** `DELETE …/devices/{id}`
# （直接销毁设备及其密钥），而这条只读取设备与签名表、算出一个布尔结论，外加一行
# 审计记录 —— 权限严格低于它已经拥有的那个。允许删设备却不允许看它是否已签名背书
# 说不通。真正的破坏性批量删除 `…/devices/{id}/delete` 仍由 `privileged.rs` 挡住。
POST /_synapse/admin/v1/users/{user_id}/devices/{device_id}/verify
