# Routes that do NOT take an auth extractor in the handler signature.
#
# Format: `METHOD PATH<TAB>kind<TAB>reason`
#   * Lines starting with `#` are comments; blank lines are skipped.
#   * `METHOD PATH` is whitespace-separated (paths contain no spaces).
#   * EXACTLY two tabs follow: kind, then a free-text reason. A missing tab is a
#     parse error so a stray tab can never silently become part of the kind.
#   * `kind` is one of:
#       public     - no credential at all; the spec (or our deployment surface)
#                    keeps the route open
#       federation - authenticated by an `X-Matrix` request signature applied in
#                    a `route_layer`, which the source extractor cannot see
#       middleware - authenticated by a `route_layer` auth middleware (e.g.
#                    `admin_auth_middleware`) rather than an extractor
#       secret     - authenticated by a shared secret / HMAC the handler (or its
#                    middleware) compares itself
#       manual     - the handler parses and validates the bearer token itself
#
# Why this table exists
# ---------------------
# SEC-15: "鉴权覆盖率" had no falsifiable definition. A route could be added with
# no auth at all and nothing failed. The invariant enforced by
# `check_route_auth.py` is now:
#
#   every route either declares `AuthenticatedUser` / `AdminUser` /
#   `OptionalAuthenticatedUser` in its handler signature, or appears here with a
#   reason.
#
# The gate is bidirectional: an entry whose route disappears, or whose handler
# later gains an auth extractor, is RED (the entry is stale). Adding a fresh
# unauthenticated route is RED until someone records why it is not authenticated.
