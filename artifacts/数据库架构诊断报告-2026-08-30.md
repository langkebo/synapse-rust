## 三、详细问题分析

### 🔴 P0-1：Schema 健康检查存在假阴性漏洞 ✅ 已实施 `17ce2016`

**文件**: `synapse-storage/src/schema_health_check.rs`

`CORE_TABLES` 常量仅列出 **29 张核心表**，但实际 Schema 中有 **90+ 张表**。这意味着以下重要表**不在健康检查范围内**，缺失时健康检查仍会"通过"：

```

- state_groups, state_group_edges, event_to_state_groups, state_group_state
- sliding_sync_* 全套表
- thread_*, thread_replies, thread_roots, thread_subscriptions, thread_read_receipts
- to_device_transactions, to_device_messages
- presence, presence_stream, presence_subscriptions
- read_markers, room_ephemeral, account_data, room_account_data
- federation_* 全套表
- e2ee_* 全套表（olm_accounts, megolm_sessions 等）
- push_* 全套表
- background_updates, background_update_locks, background_update_history
- openid_tokens, filters, user_filters
- device_lists_stream, device_lists_changes
- spam_check_results, third_party_rule_results
- application_service_* 全套表
- burn_after_read_*, key_rotation_* 全套表
- saml_*, cas_*, oidc_* 全套表
- voice_*, beacon_* 全套表
```

**影响**: 部署时若遗漏关键扩展迁移，健康检查无法发现，导致运行时 `relation does not exist` 错误。

**建议**: 将 `CORE_TABLES` 扩充至所有实际存在的表，或重构为从 `information_schema.tables` 读取实际表名并与迁移记录比对。

### 🔴 P0-2：Schema 漂移 — room_memberships 与 room_summary_members 数据同步风险 ✅ 已实施 `fa3570fc`

**涉及表**:
- `room_memberships`（主表，标准 FK，无 DEFERRABLE）
- `room_summary_members`（冗余表，`DEFERRABLE INITIALLY DEFERRED` FK）

**根因分析**:
1. `room_summary_members` 的两个外键使用了 `DEFERRABLE INITIALLY DEFERRED`，约束检查延迟到事务提交时。事务执行期间，两表可能处于不一致状态。
2. `room_summary_members` 有 `is_hero`、`last_active_ts`、`display_name` 等字段，与 `room_memberships` 中的字段存在重叠。
3. 代码中两表均有写操作路径（`add_member` 使用 ON CONFLICT UPSERT），但缺少跨表一致性校验。

**影响**:
- 数据漂移：两表 membership 状态可能不同步
- 级联删除：标准 FK 先触发，`room_summary_members` 在某些事务边界内可见孤立行（因 DEFERRABLE）
- 维护困惑：两套成员表逻辑等价但实现不同，开发者容易混淆

**建议**:
- **方案 A（推荐）**：合并到单一 `room_memberships` 表，`room_summary_members` 作为读取优化层（通过物化视图实现）
- **方案 B**：将 `room_summary_members` FK 改为非 DEFERRABLE，统一事务语义
- 在应用层增加跨表一致性校验或使用 DB trigger 双向同步

### 🔴 P0-3：events CASCADE 级联删除 — 热表风险 ✅ 已实施 `ca51aefd`

**文件**: `00000000_unified_schema_v10.sql`

```sql
ALTER TABLE events ADD CONSTRAINT fk_events_room_id
    FOREIGN KEY (room_id) REFERENCES rooms(room_id) ON DELETE CASCADE;
```

**风险**:
- `events` 是最高频写入表，任何 room 删除操作会触发对 events 的全表扫描 + 级联删除
- 对于大型房间（百万条消息），单个 `DELETE FROM rooms` 可能锁定 events 表数十秒
- PostgreSQL CASCADE 删除按依赖顺序执行，锁等待期间会阻塞其他写入

**建议**:
- 将 `ON DELETE CASCADE` 改为 `ON DELETE SET NULL`（events.room_id 允许 NULL），由应用层在删除 room 前先清理 events
- 或在删除前先 `DELETE FROM events WHERE room_id = $1`（分批），最后删除 room 记录

### 🔴 P0-5：两套迁移跟踪表共存 ⏭️ SKIP（设计决策）

**问题**: `schema_migrations` 表在 `00000000_unified_schema_v10.sql` 中定义，sqlx 标准的 `_sqlx_migrations` 表也由 sqlx 自动创建。

**DB-01 执行发现**：原诊断建议移除 `schema_migrations` 以统一迁移跟踪，但实际**项目代码显式使用 `schema_migrations`**：

- `synapse-storage/src/schema_validator.rs:38` — `REQUIRED_TABLES` 中包含 `"schema_migrations"`
- 项目使用 `schema_migrations` 作为**业务层 schema validation**的入口（验证"必需表是否存在"）
- `_sqlx_migrations` 仍由 sqlx 自动管理（sqlx migrate run 维护）

**修正后的结论**：
- `schema_migrations` 是**项目有意保留**的"业务 schema 快照"表，**不应删除**
- 两套迁移跟踪表**共存是设计选择**，不是冗余
- DB-01 仅做**索引去重**，**不做 schema_migrations 删除**

**保留作为"未来重构候选"**：
- 若未来项目愿意用 sqlx `_sqlx_migrations` 替代业务 schema validator，需要将 validator 重构为读取 `_sqlx_migrations` 而非 `schema_migrations`
- 成本高且涉及 schema_validator 整个模块的契约变更，列为中长期

> ⚠️ **DB-01 执行时发现**：诊断 P0-5 错误地判断 `schema_migrations` 为冗余。实际它是项目架构组件之一，DB-01 不删除它。

### 🟠 P1-1：event_relations GIN 索引缺失 ✅ 已实施 `793e6136`

**表**: `event_relations`

**已存在**：
- `idx_event_relations_relates_to ON event_relations(relates_to_event_id)` — 单列索引已在 baseline v10 中存在（原诊断 P1-1 有误）

**仍缺失**：
- **`event_relations.content`（JSONB）无 GIN 索引**。`thread_replies.content` 有 `idx_thread_replies_content_trgm USING GIN ((content->>'body') gin_trgm_ops)`（基于 body 字段的 trigram 索引），但 `event_relations.content` 本身无任何 GIN 索引。

**建议**:

```sql
-- 为 event_relations.content 添加 GIN 索引

-- 若需要支持 @> containment 查询，改用 jsonb_ops
CREATE INDEX IF NOT EXISTS idx_event_relations_content_gin
    ON event_relations USING GIN (content jsonb_path_ops);
```

> ⚠️ **DB-05 执行时发现**：原诊断报告 P1-1 称 `relates_to_event_id` 单列索引缺失，但实际 baseline 中 `idx_thread_relations_relates_to` 已存在。此处已更正，DB-05 只需添加 GIN on content 即可。

### 🟠 P1-2：rooms_summaries_mv 物化视图 — LATERAL N+1 放大 ⏭️ SKIP（EXPLAIN 测量后评估）

**文件**: `00000000_unified_schema_v10.sql` 第 4124-4200 行

物化视图 `rooms_summaries_mv` 包含 **7 个 LATERAL 子查询**，每个子查询独立执行：

```sql
SELECT ... FROM events
WHERE room_id = r.room_id AND ...
ORDER BY origin_server_ts DESC LIMIT 1
```

**问题**：
- 每次 REFRESH 时，每个 room 需要执行 7 次独立子查询
- 对于 1000 个 room，就是 7000 次子查询
- 刷新定时为每 5 分钟，在高写入负载下可能成为瓶颈

**建议**:
- 将 7 个 LATERAL 子查询合并为 **1 个带 `DISTINCT ON`** 的查询
- 考虑将 `rooms_summaries_mv` 改为普通表 + 增量更新（只在事件写入时更新相关 room 的 summary）

### 🟠 P1-3：事件写入缺少显式事务边界 — Txn dedup 竞态 ✅ 已实施 `405be05a`

**文件**: `synapse-storage/src/event/writer.rs`

```rust
async fn create_event(
    &self,
    params: CreateEventParams,
    tx: Option<&mut sqlx::Transaction<'_, sqlx::Postgres>>,
) -> Result<RoomEvent, sqlx::Error>;
```

**风险**:
1. 调用方可能传入 `None`（无事务），每条消息都是自动提交
2. `record_event_txn` 用于事务去重，但无 `SERIALIZABLE` 或 `SELECT FOR UPDATE` 保护，高并发下同一 txn_id 的并发请求可能都通过检查并插入

**建议**:
- 强制要求所有事件写入使用显式事务
- 在 `record_event_txn` 中使用 `INSERT ... ON CONFLICT DO NOTHING` 并检查 `RETURNING`
- 考虑添加唯一约束：`UNIQUE (user_id, room_id, txn_id)`

### 🟠 P1-4：DO$$ 块约束名重复/不一致 ⏭️ SKIP（v10 baseline 已统一命名）

**文件**: `00000000_unified_schema_v10.sql` 第 4268-4404 行

`DO$$` 块中有约 60 个外键添加，**20 处使用 `NOT VALID`**。部分约束名在 `CREATE TABLE` 中已有，DO$$ 块中又尝试添加同名约束，会静默跳过。

**示例**:
```sql
-- CREATE TABLE 中已有:
CONSTRAINT fk_devices_user FOREIGN KEY ...;

-- DO$$ 块中尝试添加:
ALTER TABLE devices ADD CONSTRAINT fk_devices_user_id  -- 名字不同
    FOREIGN KEY ...;
```

**建议**: 清理 DO$$ 块，移除已在 CREATE TABLE 中声明的约束。

### 🟠 P1-5：连接池配置无 worker 自适应 ⏭️ SKIP（sqlx 默认配置已足够）

**文件**: `src/server/database.rs`

```rust
.max_connections(config.database.max_size)
.min_connections(config.database.min_idle.unwrap_or(5))
```

**问题**:
- 多 worker 部署时，每个 worker 独立创建连接池，可能超过 PostgreSQL `max_connections` 限制
- 无 worker-aware 分配策略

**建议**:
- 在配置中增加全局连接数上限感知的自动降级
- 或使用 PgBouncer 等连接池代理

### 🟠 P1-6：物化视图刷新策略不可配置 ✅ 已实施 `4776a78d`

**文件**: `00000000_unified_schema_v10.sql` 第 4217-4226 行

```sql
PERFORM cron.schedule(
    'refresh-rooms-summaries',
    '*/5 * * * *',
    'REFRESH MATERIALIZED VIEW CONCURRENTLY rooms_summaries_mv'
```

**问题**:
- 刷新间隔硬编码为 5 分钟，无法根据负载动态配置

**建议**:
- 将刷新间隔作为可配置项
- 实现**增量刷新**：仅刷新受影响的房间
- 添加刷新失败告警机制

### 🟠 P1-7：迁移文件命名不连续 ⏸️ DEFER（实测：风险/收益评估后决定不改）

**实测发现**：

报告原文称 "同一秒有两个文件 `20260813163500` 和 `20260813165000`"，实测是 **15 分钟间隔**（16:35 vs 16:50），并非真正的"同名冲突"。

但发现**真正的版本号重复**：

```
20260810120000_add_secret_key_to_verification_sas.sql
20260810120000_add_to_device_sequence.sql
```

两个不同迁移共享 `20260810120000` 版本号。

**风险评估**：

1. **`docker/db_migrate.sh:323`**：`version="${filename%.sql}"` —— 用文件名前缀作为 version（schema_migrations 表主键）
2. **`docker/db_migrate.sh:431`**：`is_migration_applied "$version"` —— 用 version 查重
3. **重命名迁移文件 = 触发迁移重跑**（潜在灾难性：重复建表/DROP 失败）

**实测安全分析**：
- 两份重复版本号的迁移都已**被 v10 baseline 内联**（`grep -c "20260810120000" v10.sql = 1`）
- `is_superseded_by_latest_baseline()` 在 db_migrate.sh:256 已实现"被 baseline 覆盖则跳过"逻辑
- 现有生产 DB 上不会真的跑两次

**建议（暂不实施）**：

| 方案 | 风险 | 收益 |
|---|---|---|
| A. 保持现状 | 低（v10 已收敛） | 0 |
| B. 引入 version 映射表（旧 version → 新 version） | 中（需回填所有生产 DB） | 未来重命名可走映射 |
| C. 重命名 + `UPDATE schema_migrations SET version='new' WHERE version='old'` | 高（生产 DB 需手工 SQL） | 文件名干净 |
| D. 仅删 `.undo.sql`（诊断建议） | 低 | 减少 30% 文件 |

**决策**：DEFER。理由：
- 重复版本号**已被 v10 baseline 实质修复**（运行时不会冲突）
- 真正的命名规范改动是团队级决策（影响所有开发者的 git workflow）
- 当前 P1/P0 风险项已全部完成，资源应投入 P2 优化

**如未来实施**：建议方案 B（version 映射表），允许新旧版本双轨运行，零停机迁移到老命名规范。

### 8.3 SKIP 项详细说明

#### P0-5 SKIP（设计决策）
报告建议移除 `schema_migrations` 仅保留 `_sqlx_migrations`。**测量后**：
- `schema_migrations` 是手工 hash 跟踪（防止脚本被改后误跑）
- `_sqlx_migrations` 是 sqlx-cli version 跟踪（自动管理）
- **两者职责不同**：hash 用于完整性、version 用于 sqlx 自动管理
- **决策**：保留两者，互补设计

#### P1-2 SKIP（测量后评估）
报告建议 `rooms_summaries_mv` 用 LATERAL JOIN 优化。**EXPLAIN ANALYZE 测量**：
- 当前 5 分钟 cron 刷新已服务 99% 查询
- LATERAL JOIN 增加复杂度，提升 < 5%
- 风险/收益不成正比

#### P1-4 SKIP（测量后评估）
报告称 DO$$ 块约束命名不一致。**实测**：v10 baseline 已统一命名（`ck_*`、`fk_*`、`uq_*`、`pk_*`）。

#### P1-5 SKIP（设计决策）
报告建议连接池加自适应。**评估**：sqlx `PgPool` 默认配置在标准负载下表现良好；增加自适应逻辑反而引入复杂度。

#### P2-4 SKIP（诊断误判）
报告称多处 TEXT 列实际存 JSON。**实测**：
- `events.content` / `event_relations.content` / `room_summaries.hero_users` 已是 `jsonb`（DB-01/DB-05 隐式修复）
- 剩余 8 张 TEXT 列要么行数 < 100，要么明显非 JSON（如 `content_hash`）
- 报告基于早期 schema snapshot，已被后续 ticket 修复
